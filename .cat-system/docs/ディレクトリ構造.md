# ディレクトリ構造

~~~text
<development-repository>/
  .github/
    copilot-instructions.md
    agents/*.agent.md
    skills/<name>/SKILL.md
  Lifecycle/
    Issues/
      New/<issue>/issue.md
      InProgress/<issue>/issue.md
      Blocked/<issue>/issue.md
      Completed/<issue>/issue.md
      Cancelled/<issue>/issue.md
    Tasks/
      New/<task>/task.md
      InProgress/<task>/task.md
      Blocked/<task>/task.md
      Completed/<task>/task.md
      Cancelled/<task>/task.md
    Works/
      New/<work>/Work.md
      InProgress/<work>/Work.md
      Blocked/<work>/Work.md
      Completed/<work>/Work.md
      Cancelled/<work>/Work.md
    CAT/{Candidates,Draft,Reviews}/...
    TDD/Results/<work>.md
    REF/Scopes/<work>.md
  Docs/
    Constraints/                # 技術構成、開発環境、Git運用等の正本または正本リンク
    Processes/<process>/
      Process.md
      PI.md
      TCE.md
      DomainRule*.md
      CommonRule*.md
      DomainSpec*.md
  TestModels/<process>/*.md
  Room0/<repo>/                 # 開発対象の元repo
  RoomN/<worktree>/             # 作業分離用worktree
~~~

配置は論理的役割であり、既存プロジェクトのフォルダ規則に合わせて変更できる。VS Codeの`.github/agents`・`.github/skills`は設定の探索パスであり、GitのremoteがGitHubであることを意味しない。技術制約はプロジェクト既存の技術構成正本を優先し、`Docs/Constraints/`の同内容コピーを第二の正本にしない。`Room0`/`RoomN`はCATのProcessを意味しない。worktreeのGit管理・ignoreは開発環境側で保証する。


## CAT-TDDテンプレートのGit境界

CAT-TDDを任意プロジェクト用テンプレートとして利用する場合、親CAT-TDDリポジトリが追跡するのは**テンプレートと共通実行環境だけ**とする。個別プロジェクトによって内容が変わるArtifactや選択結果は、CAT-TDD自身のGit履歴へ混入させない。

親CAT-TDDでGit管理しない標準領域は次のとおり。

- `Lifecycle/**`: Issue / Task / Work、CAT Candidate/Draft/Review、TDD/REF結果。
- トップレベル`Docs/**`: 個別プロジェクトのConstraintsとconfirmed Process仕様。共通契約を置く`.cat-system/docs/**`とは別領域。
- `TestModels/**`: 個別プロジェクトのCAT仕様から導出されたTestModel。
- `Room0/**`: 対象repo。
- `RoomN/**`: 作業用worktree。
- `.github/skills/tech-*/**`: Workごとに選択導入された技術SkillのCopilot探索用コピー。
- `.github/skills/*-adapter/**`: 明示選択したproject adapterのCopilot探索用コピー。
- `.cat-system/extensions/**`: プロジェクト固有adapter/connection map。
- `.cat-flow/**`: command evidence、JUnit、context fingerprint等の一時実行状態。

上記ディレクトリ自体はclone直後から存在させるため、テンプレート側で`.gitkeep`だけを追跡してよい。`.gitignore`は追跡済み`.gitkeep`を削除しないため、領域全体をignoreしてもclone時の骨格は維持できる。

一方、次はCAT-TDDテンプレート側の共通資産なので追跡する。

- `.cat-system/{agents,skills,docs,config,scripts,optional-skills}`の共通内容。
- `.cat-system/skills/tech-*`: 利用可能な技術Skillのpool。これは「採用済み技術」ではなくテンプレート能力の集合。
- `.github/agents/*`と共通`.github/skills/*`: Copilotが初期状態で利用する共通Agent/Skill。
- ルート`README.md`、`.gitignore`、`.github/copilot-instructions.md`等のテンプレート契約。

プロジェクト固有内容を親CAT-TDDへ`git add -f`してはならない。対象repoのGit操作は`git -C Room0/<repo> ...`または`git -C RoomN/<worktree> ...`のように対象を明示する。Lifecycle/Docs/TestModels等を永続的に版管理する必要がある場合も、CAT-TDDテンプレートrepoへ混在させず、個別プロジェクト側の定めた正本・別repo・外部正本で管理する。

## Lifecycle状態は配置で表す

Issue / Task / WorkのLifecycle状態は、front matterの重複フィールドではなく**状態フォルダへの配置を正本**とする。標準状態は次の5つ。

| フォルダ | 意味 |
| --- | --- |
| `New` | 登録済みだが未着手 |
| `InProgress` | 現在進行中で、継続可能な作業がある |
| `Blocked` | 未完了だが、意味決定・外部入力・依存作業等を待ち、現在は進行不能 |
| `Completed` | 受入条件と必要な子要素・Gateを満たして完了 |
| `Cancelled` | 意図的に中止・対象外化し、完了とは扱わない |

状態変更は `<ID>` ディレクトリ全体の移動として行う。Issue / Task / WorkのIDは移動前後で変更せず、相互参照は状態を含むpathではなく安定IDを使用する。状態依存の相対path (`../InProgress/...` 等) を規範参照に使わない。

`Work`配下のCAT Draft、TestModel、局所証拠等をWorkディレクトリ内へ置く場合も、Workディレクトリ全体を移動する。`@work/`参照はWorkディレクトリ基準なので状態移動後も意味を変えない。

### 親状態の集約

- Issueは、必要なTaskが開始されたら`InProgress`へ移す。受入条件を満たし、必要なTaskが全て完了した後に`Completed`へ移す。
- Taskは、必要なWorkが開始されたら`InProgress`へ移す。Taskの完了条件を満たし、必要なWorkが全て完了した後に`Completed`へ移す。
- 親の未完了子要素のうち1つでも進行可能なら、親は原則`InProgress`に置く。`Blocked`へ移すのは、残る未完了作業が全て停止要因により進行不能な場合。
- 子要素の`Cancelled`は自動的に親を完了させない。対象外化が親の受入条件と整合することを確認する。
- 完了済み要素を再開する場合は、新しいIssueとして扱う必要があるかを判断し、同一事項の再開であれば元IDを`InProgress`へ戻して再開理由を記録する。

### 探索規約

状態フォルダはAI/人間双方の探索indexとして利用する。通常の作業選択では全履歴を走査しない。

- 新規受付: `Issues/New/`
- 現在の作業再開: `Works/InProgress/`
- 人間判断・外部依存待ちの確認: `Issues|Tasks|Works/Blocked/`
- 過去実績・回帰根拠の調査: 必要な場合だけ`Completed/`
- `Cancelled/`は履歴・判断理由を参照するときだけ探索する。

これにより、状態判定のために全`issue.md` / `task.md` / `Work.md`を開いてmetadataを読むことを標準手順にしない。


## 実運用パッケージ自身の構造

~~~text
ai_systems/
  README.md
  agents/                 # Agent定義
  skills/                 # 通常導入候補のSkill
  optional-skills/        # 明示利用時だけ使う補助Skill
  extensions/             # プロジェクト固有。明示選択時だけ導入
    <project>-adapter/
      SKILL.md
      <connection-map>.md
  docs/                   # 共通の人間向け契約・説明
  config/                 # 機械設定
    routing.json
  scripts/                # 実行コードのみ
    cat_flow.py
    cat_artifact_lint.py
    cat_compile_v2.py
    cat_install.py
  tests/                  # パッケージ保守用。導入先へ配布しない
    fixtures/             # プロジェクト非依存の最小fixture
    test_*.py
~~~

`docs/`と`config/`を分け、Markdownの規範・運用契約とJSON等の機械設定を同一ディレクトリへ混在させない。`scripts/`には実行コードだけを置き、`test_*.py`は`tests/`へ分離する。検証レイヤー(`20_検証メタ` / `30_検証生成物`)の具体プロジェクト成果物を、実運用パッケージの自己テストfixtureとして参照しない。

## 正本を二重化しない

XPlayServerではGoogle Drive現行文書を仕様正本とする。上の`Docs/`に自動複製する場合は、取得時点・URL・版を持つ読取専用snapshotであることを明示し、別の正本にしない。コードの実装事実は対象Gitリポジトリの実際のbranch/commitで確認する。XPlayServerの現行remoteは同プロジェクトの入口に従って確認する。Driveを更新したら再取得して内容と配置を検証した後に実装する。

## Artifactの所属

- `Issues/{New,InProgress,Blocked,Completed,Cancelled}`: 課題、要求、意味未決定の列挙。配置がLifecycle状態を表す。
- `Tasks/{New,InProgress,Blocked,Completed,Cancelled}`: Process責務、子Workの依存関係。配置がLifecycle状態を表す。
- `Works/{New,InProgress,Blocked,Completed,Cancelled}`: PI/TCE差分と個別成果・複数repoの状態。配置がLifecycle状態を表す。
- `CAT/Candidates`: コード・テスト・現場観測からの未承認候補。
- `CAT/Draft`: 規範入力からの仕様案。レビューと意味承認前の非正本。
- `Docs/Processes`: confirmedのProcess/PI/TCE/Common Rule/Domain Rule/Domain Specification。Drive正本の場合はリンク/同期方針を優先。
- `TestModels`: confirmed仕様からのモデル。
- `TDD/Results`: Red、Green、CIの実測結果。
- `REF/Scopes`: 意味保存の対象と必要な回帰。

仕様の状態遷移図はconfirmed PI/TCEからの派生物として生成してよい。図は入力仕様の代用品でもProcess合成の一般証明でもない。

## Skill・プロジェクト文書の配置

- `skills/tech-<technology>/SKILL.md`: 技術依存の再利用手順。採用技術の明示されたcomponentへ必要時に選択する。
- `extensions/<project>-adapter/SKILL.md`: プロジェクト固有の手続きが残る場合だけ置く。共通`skills/`へ混在させず、明示選択時だけ導入する。
- `extensions/<project>-adapter/<connection-map>.md`: Adapter専用の参照マップ。プロジェクト正本そのものではない。
- `docs/プロジェクト適用.md`: 全プロジェクト共通の適用契約。


## 実行ツールの実際の配置（Copilot）

共通ファイルの導入は`scripts/cat_install.py --work <Work.md> --project-root <workspace>`をまず**plan-only**で実行し、変更を確認してから`--apply`。`.github/agents`と採用済み`.github/skills`へAgent/Skillを配置し、`.cat-system/{scripts,docs,config,agents,skills,optional-skills}`へ共通実行物だけを配置する。選択したAdapterだけ`.cat-system/extensions/<adapter>/`へ追加する。未採用tech Skillと未選択extensionは配置しない。`Work.md`は`Lifecycle/Works/<Lifecycle状態>/<work>/Work.md`を標準位置とし、状態変更時はWorkディレクトリ全体を移動する。旧`work.json`は移行用の互換入力に限る。`.cat-flow/`は証拠/一時JUnitであり、秘密・ログの混入を避けてGitから除外する。ユーザ作成Agent/Skillとの名前衝突は停止し、明示的な上書き指示なしに置換しない。`.github`はCopilotの設定pathであり、GitリモートはGitHubに限定しない。導入先の資料がGit外正本ならそのリンクを保持する。

## 配置検証

`cat_install.py`は書込み前に、導入後パスを基準としてMarkdownの相対リンクと`.cat-system/...`参照を検査する。未解決参照が1件でもあれば導入を停止する。`@work/`・無印Compilation pathはWorkディレクトリ、`@workspace/`はworkspace、`@repo:<name>/`は宣言repo、`@package/`はCAT packageを境界とし、`..`による境界外参照を拒否する。

パッケージ自己テストでは、実際に一時workspaceへ導入して`route`・参照解決・選択Skillだけの配布・導入済みruntimeでのCompilation境界を確認する。Copilot自身のAgent起動・Skill自動選択・ツール権限制御は外部実行環境の検証対象として別に扱う。
