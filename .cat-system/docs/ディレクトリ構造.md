# ディレクトリ構造

~~~text
<development-repository>/
  .github/
    copilot-instructions.md
    agents/*.agent.md
    skills/<name>/
      SKILL.md
      scripts/            # Skill固有の決定論的補助コードがある場合
  Lifecycle/
    Issues/
      New/<issue>/issue.md
      InProgress/<issue>/issue.md
      Blocked/<issue>/issue.md
      Completed/<issue>/issue.md
      Cancelled/<issue>/issue.md
    Tasks/
      New/<task>/task.md
      InProgress/<task>/task.md
      Blocked/<task>/task.md
      Completed/<task>/task.md
      Cancelled/<task>/task.md
    Works/
      New/<work>/Work.md
      InProgress/<work>/Work.md
      Blocked/<work>/Work.md
      Completed/<work>/Work.md
      Cancelled/<work>/Work.md
    CAT/{Candidates,Draft,Reviews}/...
    TDD/Results/<work>.md
    REF/Scopes/<work>.md
  Docs/
    Constraints/                # 技術構成、開発環境、Git運用等の正本または正本リンク
    Processes/<process>/
      Process.md
      PI.md
      TCE.md
      DomainRule*.md
      CommonRule*.md
      DomainSpec*.md
  TestModels/<process>/*.md
  Room0/<repo>/                 # 開発対象の元repo
  Room1/<repo>/                 # 並列作業空間1のrepo別Git worktree（複数repo可）
  Room2/<repo>/                 # 並列作業空間2のrepo別Git worktree（複数repo可）
  ...                          # 必要なだけRoom3、Room4、...を追加
~~~

配置は論理的役割であり、既存プロジェクトのフォルダ規則に合わせて変更できる。VS Codeの`.github/agents`・`.github/skills`は設定の探索パスであり、GitのremoteがGitHubであることを意味しない。技術制約はプロジェクト既存の技術構成正本を優先し、`Docs/Constraints/`の同内容コピーを第二の正本にしない。`Room0`は元repoの配置先であり、`Room1`、`Room2`、...は並列作業空間の識別子である。`RoomN`のNは正の整数を表す説明用記号であり、文字どおりの`RoomN`ディレクトリやGitリポジトリは作らない。1つの番号付きRoomには複数repoのworktreeを置ける。同一repoのworktreeを複数Roomに作る場合はGitの制約に従い別ブランチを使う。RoomはCATのProcessではない。


## 番号付きRoomの構造と作成

`Room0/<repo>/`は対象repoの元Git作業ツリーである。並列作業する場合に`Room1/<repo>/`、`Room2/<repo>/`等を追加する。各Roomは**リポジトリ単位ではなく作業空間単位**なので、同じRoom番号に複数repoのworktreeを並べてよい。

~~~text
Room0/ repo-A/ repo-B/
Room1/ repo-A/ repo-B/
Room2/ repo-A/ repo-B/
~~~

`Room1/repo-A`を用意する例（`Room1/`は事前作成）：`git -C Room0/repo-A worktree add ../../Room1/repo-A -b <branch>`。各worktreeは元repoのGit管理下にあり、別repoとしてcloneしない。worktreeの追加・一覧・削除は`git worktree`コマンドで管理し、親CAT-TDDリポジトリのGit管理とは区別する。

## CAT-TDDテンプレートのGit境界

CAT-TDDを任意プロジェクト用テンプレートとして利用する場合、親CAT-TDDリポジトリが追跡するのは**テンプレートと共通実行環境だけ**とする。個別プロジェクトによって内容が変わるArtifactや選択結果は、CAT-TDD自身のGit履歴へ混入させない。

親CAT-TDDでGit管理しない標準領域は次のとおり。

- `Lifecycle/**`: Issue / Task / Work、CAT Candidate/Draft/Review、TDD/REF結果。
- トップレベル`Docs/**`: 個別プロジェクトのConstraintsとconfirmed Process仕様。共通契約を置く`.cat-system/docs/**`とは別領域。
- `TestModels/**`: 個別プロジェクトのCAT仕様から導出されたTestModel。
- `Room0/**`: 対象repo。
- `Room1/**`・`Room2/**`等: 各Room内のrepo別worktree。
- `.github/skills/<selected-technology-skill>/**`: `config/routing.json`からWorkごとに選択導入された技術SkillのCopilot探索用コピー。自作`tech-*`だけでなく登録済み外部Skill名も含む。
- `.github/skills/*-adapter/**`: 明示選択したproject adapterのCopilot探索用コピー。
- `.cat-system/extensions/**`: プロジェクト固有adapter/connection map。
- `.cat-flow/**`: command evidence、JUnit、context fingerprint等の一時実行状態。

`Room0/`やLifecycle等の固定骨格にはテンプレート側で`.gitkeep`を置ける。一方、番号付き`Room1/`以降は必要になった時点で作成し、親Gitへ追跡させない。`.gitignore`の`/Room[1-9]*/`は番号付きRoomをまとめて除外するためのGit globであり、部屋番号の有効性は運用契約（先頭ゼロなしの正の整数）で定義する。

一方、次はCAT-TDDテンプレート側の共通資産なので追跡する。

- `.cat-system/{agents,skills,docs,config,scripts,optional-skills}`の共通内容。
- `ai_systems/skills/`内で`config/routing.json`に登録された技術Skill: 利用可能な技術Skillのsource pool。これは「採用済み技術」ではなくテンプレート能力の集合。導入先`.cat-system/skills/`には選択済みだけを配置する。
- `.github/agents/*`と共通`.github/skills/*`: Copilotが初期状態で利用する共通Agent/Skill。
- ルート`README.md`、`.gitignore`、`.github/copilot-instructions.md`等のテンプレート契約。

プロジェクト固有内容を親CAT-TDDへ`git add -f`してはならない。対象repoのGit操作は`git -C Room0/<repo> ...`または`git -C Room1/<repo> ...`のように対象を明示する。Lifecycle/Docs/TestModels等を永続的に版管理する必要がある場合も、CAT-TDDテンプレートrepoへ混在させず、個別プロジェクト側の定めた正本・別repo・外部正本で管理する。

## Lifecycle状態は配置で表す

Issue / Task / WorkのLifecycle状態は、front matterの重複フィールドではなく**状態フォルダへの配置を正本**とする。標準状態は次の5つ。

| フォルダ | 意味 |
| --- | --- |
| `New` | 登録済みだが未着手 |
| `InProgress` | 現在進行中で、継続可能な作業がある |
| `Blocked` | 未完了だが、意味決定・外部入力・依存作業等を待ち、現在は進行不能 |
| `Completed` | 受入条件と必要な子要素・Gateを満たして完了 |
| `Cancelled` | 意図的に中止・対象外化し、完了とは扱わない |

状態変更は `<ID>` ディレクトリ全体の移動として行う。Issue / Task / WorkのIDは移動前後で変更せず、相互参照は状態を含むpathではなく安定IDを使用する。状態依存の相対path (`../InProgress/...` 等) を規範参照に使わない。

`Work`配下のCAT Draft、TestModel、局所証拠等をWorkディレクトリ内へ置く場合も、Workディレクトリ全体を移動する。`@work/`参照はWorkディレクトリ基準なので状態移動後も意味を変えない。

### 生成主体と責務

- `Issue`: 通常の人間向け入力単位。人間は要求・問題・目的・完了条件・対象外・未決定事項を記述できればよく、CAT/TDDのProcess分解を要求しない。
- `Task`: 新規Issueを受け付けたAIの`cycle-scope-divider`が、IssueをProcess責務単位へ分解して生成する。
- `Work`: `cycle-scope-divider`がTaskを独立して仕様化・検証できる仕様差分へ分解して生成する。`Work.md`が人間可読であることは、人間が手作成することを意味しない。
- 意味上の選択が不足する場合、AIはIssue/Task/Workへ推測で補完せず、人間へ決定を返す。

### 親状態の集約

- Issueは、必要なTaskが開始されたら`InProgress`へ移す。受入条件を満たし、必要なTaskが全て完了した後に`Completed`へ移す。
- Taskは、必要なWorkが開始されたら`InProgress`へ移す。Taskの完了条件を満たし、必要なWorkが全て完了した後に`Completed`へ移す。
- 親の未完了子要素のうち1つでも進行可能なら、親は原則`InProgress`に置く。`Blocked`へ移すのは、残る未完了作業が全て停止要因により進行不能な場合。
- 子要素の`Cancelled`は自動的に親を完了させない。対象外化が親の受入条件と整合することを確認する。
- 完了済み要素を再開する場合は、新しいIssueとして扱う必要があるかを判断し、同一事項の再開であれば元IDを`InProgress`へ戻して再開理由を記録する。

### 探索規約

状態フォルダはAI/人間双方の探索indexとして利用する。通常の作業選択では全履歴を走査しない。

- 新規受付: AIが`Issues/New/`を読み、`cycle-scope-divider`でTask/Workへ分解する
- 現在の作業再開: `Works/InProgress/`
- 人間判断・外部依存待ちの確認: `Issues|Tasks|Works/Blocked/`
- 過去実績・回帰根拠の調査: 必要な場合だけ`Completed/`
- `Cancelled/`は履歴・判断理由を参照するときだけ探索する。

これにより、状態判定のために全`issue.md` / `task.md` / `Work.md`を開いてmetadataを読むことを標準手順にしない。


## 実運用パッケージ自身の構造

~~~text
ai_systems/
  README.md
  agents/                 # Agent定義
  skills/                 # 通常導入候補のSkill
  optional-skills/        # 明示利用時だけ使う補助Skill
  extensions/             # プロジェクト固有。明示選択時だけ導入
    <project>-adapter/
      SKILL.md
      <connection-map>.md
  docs/                   # 共通の人間向け契約・説明
  config/                 # 機械設定
    routing.json
  scripts/                # 複数Skillから共有する実行コード
    cat_flow.py
    cat_compile_v2.py
    cat_install.py
    cat_package_lint.py
    catlib/                # CLI間で共有する内部ライブラリ。直接の運用入口ではない
      common.py
      markdown.py
      work.py
  skills/
    cat-artifacts/
      SKILL.md
      scripts/cat_artifact_scaffold.py
    cycle-management/
      SKILL.md
      scripts/cat_lifecycle.py
    cat-specification-gate/
      SKILL.md
      scripts/cat_artifact_lint.py
    tech-vitest/
      SKILL.md
      scripts/cat_vitest_renderer.py
  tests/                  # パッケージ保守用。導入先へ配布しない
    fixtures/             # プロジェクト非依存の最小fixture
    test_*.py
~~~

`docs/`と`config/`を分け、Markdownの規範・運用契約とJSON等の機械設定を同一ディレクトリへ混在させない。トップレベル`scripts/`には複数Skillが共有する実行コードだけを置き、単一Skillに閉じるコードは`skills/<name>/scripts/`へ置く。共有CLIの内部実装は`scripts/catlib/`へ分け、運用上の入口としない。`test_*.py`は`tests/`へ分離する。検証レイヤー(`20_検証メタ` / `30_検証生成物`)の具体プロジェクト成果物を、実運用パッケージの自己テストfixtureとして参照しない。

## 正本を二重化しない

XPlayServerではGoogle Drive現行文書を仕様正本とする。上の`Docs/`に自動複製する場合は、取得時点・URL・版を持つ読取専用snapshotであることを明示し、別の正本にしない。コードの実装事実は対象Gitリポジトリの実際のbranch/commitで確認する。XPlayServerの現行remoteは同プロジェクトの入口に従って確認する。Driveを更新したら再取得して内容と配置を検証した後に実装する。

## Artifactの所属

- `Issues/{New,InProgress,Blocked,Completed,Cancelled}`: 通常は人間が入力する課題・要求・目的・完了条件・意味未決定事項。AIが受付内容を整理して記録してもよい。配置がLifecycle状態を表す。
- `Tasks/{New,InProgress,Blocked,Completed,Cancelled}`: AIの`cycle-scope-divider`がIssueから生成するProcess責務単位と子Workの依存関係。配置がLifecycle状態を表す。
- `Works/{New,InProgress,Blocked,Completed,Cancelled}`: AIの`cycle-scope-divider`がTaskから生成する、独立検証可能なPI/TCE等の仕様差分と個別成果・複数repoの状態。配置がLifecycle状態を表す。
- `CAT/Candidates`: コード・テスト・現場観測からの未承認候補。
- `CAT/Draft`: 規範入力からの仕様案。レビューと意味承認前の非正本。
- `Docs/Processes`: confirmedのProcess/PI/TCE/Common Rule/Domain Rule/Domain Specification。Drive正本の場合はリンク/同期方針を優先。
- `TestModels`: confirmed仕様からのモデル。
- `TDD/Results`: Red、Green、CIの実測結果。
- `REF/Scopes`: 意味保存の対象と必要な回帰。

仕様の状態遷移図はconfirmed PI/TCEからの派生物として生成してよい。図は入力仕様の代用品でもProcess合成の一般証明でもない。

## Skill・プロジェクト文書の配置

- `skills/tech-<technology>/`: 自作する技術依存Skillの標準配置。`SKILL.md`に加え、その技術だけで使う決定論的renderer/adapter等は同Skillの`scripts/`へ置く。採用技術の明示されたcomponentへ必要時に選択する。外部Skillは上流名を維持して`config/routing.json`へ明示登録できる。
- `extensions/<project>-adapter/SKILL.md`: プロジェクト固有の手続きが残る場合だけ置く。共通`skills/`へ混在させず、明示選択時だけ導入する。
- `extensions/<project>-adapter/<connection-map>.md`: Adapter専用の参照マップ。プロジェクト正本そのものではない。
- `docs/プロジェクト適用.md`: 全プロジェクト共通の適用契約。


## 実行ツールの実際の配置（Copilot）

共通ファイルの導入は`scripts/cat_install.py --work <Work.md> --project-root <workspace>`をまず**plan-only**で実行し、変更を確認してから`--apply`。`.github/agents`と採用済み`.github/skills`へAgent/Skillディレクトリ一式を配置し、`.cat-system/{scripts,docs,config,agents,skills,optional-skills}`へ共通実行物と選択済みSkill一式を配置する。Skillの`scripts/`・`references/`・`assets/`も`SKILL.md`と同じ選択単位で扱う。選択したAdapterだけ`.cat-system/extensions/<adapter>/`へ追加する。未採用tech Skillと未選択extensionは配置しない。`Work.md`は`Lifecycle/Works/<Lifecycle状態>/<work>/Work.md`を標準位置とし、状態変更時はWorkディレクトリ全体を移動する。旧`work.json`は移行用の互換入力に限る。`.cat-flow/`は証拠/一時JUnitであり、秘密・ログの混入を避けてGitから除外する。ユーザ作成Agent/Skillとの名前衝突は停止し、明示的な上書き指示なしに置換しない。`.github`はCopilotの設定pathであり、GitリモートはGitHubに限定しない。導入先の資料がGit外正本ならそのリンクを保持する。

## 配置検証

`cat_install.py`は書込み前に、導入後パスを基準としてMarkdownの相対リンクと`.cat-system/...`参照を検査する。未解決参照が1件でもあれば導入を停止する。`@work/`・無印Compilation pathはWorkディレクトリ、`@workspace/`はworkspace、`@repo:<name>/`は宣言repo、`@package/`はCAT packageを境界とし、`..`による境界外参照を拒否する。

パッケージ自己テストでは、実際に一時workspaceへ導入して`route`・参照解決・選択Skillだけの配布・導入済みruntimeでのCompilation境界を確認する。Copilot自身のAgent起動・Skill自動選択・ツール権限制御は外部実行環境の検証対象として別に扱う。
