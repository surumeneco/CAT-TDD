# 開発フロー

## フロー選択

CAT-TDDは単一の状態機械ではない。起点と目的で次のflowを選択し、必要な場合だけ別flowへhandoffする。

| Flow | 起点 | 完了対象 |
| --- | --- | --- |
| `spec-implementation` | confirmed Process / PI / TCE等 | confirmed仕様に適合するproduction implementation |
| `issue-work` | Issue / bug | IssueをTask/Workへ分解し、work kindに応じた処理または別flowへのhandoff |
| `code-to-spec` | code / tests / logs | 証拠付きCandidateと、規範判断を経た仕様 |
| `refactor` | commit / diff / 明示範囲 | 外部意味を変えない内部構造変更 |
| `spec-test-sync` | Confirmed仕様 + 対象repo / test範囲 | 既存実装へ仕様由来テストを同期し、別に実行結果を記録 |

Issue、仕様化、TDD、Refactorを一つの必須直列工程へ連結しない。analysis / documentation / verificationだけのIssueはTDDを経ずに完了できる。Refactorはimplementationの必須後段ではない。

## 共通scope-ordering

Task/Workを作成したら、実作業の前にparentとdepends-onから依存graphを構成する。意味上の依存関係は仕様または`cycle-scope-divider`が与え、cycle検出、depth算出、readyな最深scope列挙は`scripts/cat_scope_order.py`が機械処理する。

~~~text
scope graph
  → cycle検出
  → depends-on充足確認
  → incomplete child確認
  → ready集合
  → 最大depthのscopeから実行
~~~

cycleがある場合は順序を捏造せずblockedとする。独立した最深scopeは並列readyとしてよい。

## spec-implementation

~~~text
assembled confirmed specification
→ process-closure
→ TestModel compiler
→ model-conformance
→ deterministic test-vector selector
→ Queue compiler
→ current Queue item
→ Test renderer
→ Red runner
→ Red reason validator
   └ inconclusive時だけ tdd-checker
→ tdd-implementer
→ Green / scoped regression runner
→ Queue State Manager
→ 次のcurrent item
→ implementation-conformance
   └ inconclusive obligationだけ cat-implementation-reviewer
→ project integration policy
~~~

TestModel、Queue、generated testは派生成果物であり、confirmed仕様にない意味を追加しない。1 TDD cycleで新規生成する実行可能テストはcurrent item 1件だけとする。Green後のRefactorは任意であり、必要なら独立`refactor` flowを開始する。

### CAT適合性Gate

- `process-closure`: assembled specificationの到達可能領域が閉じているか。
- `model-conformance`: source semanticsがTestModelへ欠落なく写り、model独自意味がないか。
- `implementation-conformance`: Interface / Capability / Behavior / Invariant / Cross-process / Domain / implementation constraintのobligationが評価済みか。

GreenやCI成功をこれらのGateへ読み替えない。


## spec-test-sync

既存のproduction implementationを変更せず、仕様に基づくテストの新規生成・再生成・差分同期だけを行う独立フロー。TDDのRed GateやExecution Queue（current=1）を流用しない。最初からGreenなら同期成功と実行成功を別の結果として記録する。

~~~text
Confirmed Process/PI/TCE + approved decision
→ process-closure
→ TestModel compiler
→ model-conformance
→ deterministic vectors
→ suite-plan（全vector・現Manifest・disk hash）
→ suite-sync（generated tests / Manifestだけ書込み）
→ suite-validate
→ suite-run（実行可能なproject runner）
→ suite-result（同期状態とGreen/Red/not-runを分離）
~~~

機械実装は `scripts/cat_spec_test_sync.py`。初期対応rendererはVitestで、技術bindingを必要とする。WorkのCompilationにProcess/PI/TCE/Model/Vectors/Bindingを指定し、Confirmed決定参照と同じWorkに対する`process-closure`・`model-conformance`の新鮮なScript証拠を要求する。未confirmed、unsupported、stale、書込み所有権不明はblockedとする。

`plan / sync / verify / run / report`はrepo HEADを固定して実行する。同期対象はManifestで生成所有権が確認できるファイルだけとし、手書きテスト・production source・TDD Queueは変更しない。非選択になった既存生成ファイルは自動削除せず保持する。Redは実装と規範仕様の相違を表す可能性があるが、同期処理自体の失敗と混同せず、実装修正は別Issueへ渡す。

詳細なCLIとManifest契約は[機械的変換](機械的変換.md)を参照する。

## issue-work

人間はIssueを入口としてよく、Task/Workを手作成する必要はない。`cycle-scope-divider`がProcess単位のTaskと独立検証可能なWorkへ分解する。Workは`flow`、`work_kind`、`parent`、`depends_on`を保持する。

work kindがimplementationならconfirmed仕様成立後に`spec-implementation`へhandoffする。`test-maintenance`はConfirmed仕様を入力として`spec-test-sync`へhandoffする。specificationは仕様化専用の別flowを作らず`issue-work`内の仕様化Workとして`spec → spec-closure`を実行する。analysis / documentation / verificationならそのWorkの受入条件で完了する。

## code-to-spec

~~~text
code / tests / logs
→ evidence extraction
→ CAT Candidate
→ ambiguity / conflict review
→ normative decision
→ confirmed specification when authorized
~~~

実装事実を正しい仕様へ自動昇格させない。このflowは原則production codeを変更しない。実装変更が必要なら別の`spec-implementation`またはIssueを開始する。

## refactor

~~~text
commit / diff
→ preserved semantics resolution
→ dependency / hierarchy graph
→ deepest ready scope
→ refactor-baseline runner
→ refactor Agent guard（baselineの現行source一致を再検証）
→ refactor
→ unchanged-oracle regression
~~~

behavior changeが必要になった時点でRefactorを停止し、仕様変更またはIssueへhandoffする。

## Executor選択

Stageの存在はAI Agentの起動を意味しない。`routing.json`のexecutorを直接使用する。

~~~text
script/compiler/validatorで確定
  → AIを起動しない

validator = inconclusive
  → conditional reviewerだけ起動

意味決定が必要
  → normative authorityへ

外部状態
  → providerから再取得
~~~

機械検査の`failed`・`blocked`・`stale`だけでなく、`inconclusive`をReviewerの自由記述やWorkのReview参照文字列だけで**機械Gateの`passed`に変更しない**。conditional reviewerは未証明の意味を分析・Review Artifactへ記録する役割であり、機械的なConformance verdictと区別する。`cat_flow.py status`はWork宣言のReview参照を`review_claims: unverified-claim`として報告し、Gateの通過条件には使用しない。

## Handoff

flow間handoffは別flowの開始である。confirmedへの昇格は通常Agentではなく、明示されたnormative decisionを入力とする専用authority executor `cat_promote.py`だけが行う。

`cat_flow.py handoff --stage <stage>`は、Work ID、flow/stage、規範参照とhash、permissions、未解決事項、必要なevidence参照、stale情報、next actionを構造化して渡す。長い自由文handoffを正本にしない。書込みを持つAgent stageでは`handoff`がwrite guard baselineを自動開始し、Agent終了後に`guard --phase finish`が`passed`になるまで次stageへhandoffできない。標準`Lifecycle/Works`配置ではguard開始時にdeepest-readyも再検査する。
