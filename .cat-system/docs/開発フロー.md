# 開発フロー

## 開始経路

| 入口 | 現状確認 | 意味決定 |
| --- | --- | --- |
| 確定済み仕様 | 正本と版を取得し整合性を検査 | 既決定を再設計しない |
| 新機能Issue | Processと外部観測差を抽出 | 確定不能な分岐だけを未決定化 |
| bug | 規範TCEと実現された結果の差を特定 | 規範が既定なら意味の変更なし |
| 既存コード→仕様 | 検索範囲・コード・テスト・ログを証拠台帳化 | candidateから規範へ自動昇格しない |
| refactor/移行 | 保存すべきPI/TCEと制約を固定 | 観測差が必要なら別途仕様改訂 |

通常の新規開発では、人間はIssueとして要求・問題・目的・観測可能な完了条件・対象外・未決定事項を提示する。人間にTaskやWorkへの分解を要求しない。新規Issueを受け付けたAIは、orchestratorから`cycle-scope-divider`へ委譲し、IssueをProcess単位のTaskと、単独で仕様化・検証できる仕様差分のWorkへ分解する。意味上の選択がIssueや規範正本だけでは確定できない場合、その選択だけを人間へ差し戻し、AIが便宜的に補完しない。

~~~text
人間: Issue
  ↓
AI: orchestrator → cycle-scope-divider
  ↓
Task: Process責務単位
  ↓
Work: 独立して仕様化・検証できる仕様差分
~~~

ファイル数・commit数とWork数を一致させない。Processが階層化される場合は親の外部契約を確定し、次いで子の接続を具体化する。跨ぐrepoは同じWorkに複数の実装・検証状態を持つ。


## Lifecycle状態

Issue / Task / Workの進捗状態は`Lifecycle/{Issues,Tasks,Works}/<state>/<id>/`の配置で表し、同じ状態をfront matterへ重複記録しない。標準stateは`New / InProgress / Blocked / Completed / Cancelled`。

- `New`: 未着手。
- `InProgress`: 着手済みで、現在継続可能な作業がある。
- `Blocked`: 未完了だが、意味決定・外部入力・依存関係等を待ち、残作業を進められない。
- `Completed`: その要素の受入条件を満たした。
- `Cancelled`: 意図的に中止・対象外化した。

開始時は対象stateだけを探索する。新規Issue処理ではAIが`Issues/New/`を入口としてIssueを読み、`cycle-scope-divider`でTask/Workを生成する。継続作業は`Works/InProgress/`、エスカレーション対象は`Blocked/`を入口とし、`Completed/`全件を通常の探索対象にしない。

状態遷移はIDディレクトリ全体の移動として行う。Issue / Task / Work IDは不変で、相互参照は状態を含むpathではなくIDを使う。Work内の`@work/`参照はWorkディレクトリ基準なので、ディレクトリ全体の状態移動では変更しない。 機械的な移動自体は`python .cat-system/skills/cycle-management/scripts/cat_lifecycle.py move --kind <issue|task|work> --id <id> --to <state>`へ委譲し、スクリプトは移動先の意味的妥当性を判断しない。

親Issue/Taskは、残る未完了子要素に進行可能なものがある限り`InProgress`とする。残る未完了子要素が全て停止している場合だけ`Blocked`とする。`Completed`への移動は子要素の配置だけで自動決定せず、親自身の受入条件も確認する。

Process / PI / TCE / CommonRule / DomainRule / DomainSpec / TestModelはSemantic Artifact、Candidate / Work / Gate / execution evidenceはLifecycle/Evidence Artifactとして扱う。JUnit、Git、runner、command等の実行情報をSemantic Artifactへ持ち込まない。

## ゲート

~~~text
Intake → Candidate / confirmed source → Draft
       → Closure and semantic review → Confirmed specification
       → Test Model → test generation → independent test review
       → Red evidenced → implementation → Green evidenced
       → refactor scope fixation → Refactor with unchanged oracle → regression/constraints
       → CI (if configured) → review/merge (project workflow) → deployment → real-use verification
~~~

各ゲートは`passed`・`blocked`・`not-run`・`inconclusive`を区別し、外部ゲートには必要に応じて`not-applicable`を使う。意味レビュー、oracleレビュー、Red理由レビュー、PR/MR、CI、merge、deployment、real-useはWorkの`Gates`へ証拠参照を持つ。`confirmed`は規範的な決定主体と出典を必須とする。`candidate`は観測された実装、`draft`は確定入力の仕様表現、`unknown`は意味/証拠不足、`conflict`は出典間の競合。機械lintのpassは意味承認にならない。

### 仕様ゲート

Processの境界・内部仕様状態・観測能力・作用能力、PIの相手Process・方向・Presence、Triggerの発生源、TCEの振る舞い単位、Conditionの参照状態、Effectの作用先、共通規則、領域別仕様、親子接続、決定出典を点検する。TCEの`Coverage requirement`は要求であって証明結果ではない。Conditionの網羅/重複を機械的に証明できない場合は`unproven`として手動レビューと限界を記録する。

### テストモデルゲート

仕様上の到達可能領域、許容結果集合、状態遷移、変更されない宣言済み作用先の対応を検査する。具体値、PICT、variant、E2Eの選択と、モデルの意味保存は別の判定。

### TDDゲート

Redは新しい対象テストが期待理由で失敗した実行証拠であり、「全体の失敗がちょうど1件」を要件にしない。Greenは対象および関連回帰の実行成功。失敗中テストを削除・期待値変更してGreenにしてはならない。制約lint、CI、実際のブラウザ、DB、Bot疎通は別の証拠。

### 統合ゲート

Gitのcommit/push、ホストが提供するレビュー要求（PR/MR等）、CI、mergeを別状態にする。GitHubを必須とせず、レビュー・CIの提供状況と承認方針はプロジェクト文書から確認する。マージ状態とデプロイ状態を独立させる。複数repoで一方だけmerge済みでも全体完了ではない。人間の実操作で発見した問題を、観測出典とともに次のCandidate/Workおよび再発防止テストへ戻す。

## 停止条件

意味を変える選択が複数あるとき、テストのoracleに規範がないとき、外部副作用の許容結果が決まらないときは該当Workを`Lifecycle/Works/Blocked/`へ移す。Gate上の`blocked`は個別検査結果、フォルダ上の`Blocked`はWork全体の進行不能状態であり、混同しない。根拠が同じままAIレビューを無限に繰り返さない。周辺の独立Workは継続できる。

## 技術別能力の選択

開始時にプロジェクト入口から採用技術と実行環境を読み取る。TestModel以前のCAT意味論は特定言語に依存させず、TestModelから実行テストへの変換・型/DB/UI固有の検証・具体コマンドは該当する`tech-*` Skillと現行技術構成文書に従う。プロジェクト固有の文書取得・検証手続きがある場合だけ`<project>-adapter`を追加する。選択規則は[プロジェクト適用](プロジェクト適用.md)。


## AIとスクリプトの実行分界

[AI実行契約](AI実行契約.md)をAI工程の入口とし、Work生成後の機械的入口を`scripts/cat_flow.py`とする。Issue→Task→Workの分解は`cycle-scope-divider`が意味的に行い、`cat_flow.py`はその分解を決定しない。Work情報は`Work.md`のfront matterと表で最低限の形・出典・状態・対象技術・コマンドを固定し、`cat_flow.py`が内部`cat-work/v1`へ正規化する。`validate/route/git/status/handoff`は意味判断をせず実行できる。対象Artifactが`markdown-v2`の機械変換サブセットなら`compile`でモデル→テストを再現する。対応外ではAgentが人間の規範から記述し、レビューを介す。**変換器対応を増やすことはWork完了条件ではない。**

`run`は`mode: implementation`のWorkだけで宣言済みコマンドを`--execute`で起動し、その呼出しのexit code/JUnit報告書/入力・出力hashを記録する。Redの対象失敗は機械的に検出できるが、原因の仕様適合性は`inconclusive`としてレビューへ渡す。Green/回帰はJUnitの当該スコープ成功のみ。テスト実行と本番、Gitローカル差分とGitHub/GitLab上のレビュー結果は分離する。Work manifest・入力・出力・JUnitに加え、実行cwdのcontext fingerprintが変化すれば証拠を失効する。

作業再開では`cat_flow.py handoff --work <Work.md>`で未確定・未実行ゲートを取得し、AIが現行の規範文書/リポジトリを**再取得**して不整合を確かめる。scriptの`status`はプロバイダCI、merge、deploy、人間の実操作成功を自動証明しない。

## 実運用移行の判定

本節は既存の概念的ゲートを変更しない。CLIの形式検査や状態記録だけで、上記フローが**実機で強制されている**とは扱わない。

- `tdd-reviewer`は`test-review`、`ref-scoper`は`refactor-scope`として`config/routing.json`に独立工程を持つ。生成担当と審査担当、対象固定と変更実行を同一工程へ畳み込まない。
- RedのJUnit失敗は観測できるが、期待理由の承認から実装工程への遷移を共通CLIが表現していない。期待したRed理由は`red-review` Gateへ記録する。外部ゲートを含む報告証拠が全て揃った場合のみ`reported-complete/unverified-external-evidence`まで進み、外部出典再取得前にverified completeとは呼ばない。
- 仕様の意味承認、Git/CI/merge、deploy、人間による実確認は各々別の出典・版・実行権限を必要とする。Workに`confirmed`等を記入するだけでは代替できない。
- 通常運用に先立ち、削除を含むGit差分・`shadow`書込み・未宣言依存の証拠失効・導入後参照という**否定テスト**を通す。次にCopilot実機のAgent受渡と小規模実Workを2経路（確定仕様／既存コードからのbug）で検証する。

改善作業自体も通常のIssue/Task/Workとして管理し、修正対象・受入条件・検証証拠を個別に持つ。CAT変換器の対応サンプル数は受入条件としない。
