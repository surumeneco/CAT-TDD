# プロジェクト適用・技術Skill選択

## 責務の四層

| 層 | 保持するもの | 保持しないもの |
| --- | --- | --- |
| 共通Agent / CAT・Cycle・TDD・Refactor Skill | 役割、意味・検証ゲート、Git操作の一般契約 | 特定製品名、技術スタックの固定、特定forgeのAPI |
| 技術Skill（`tech-*`） | 言語・フレームワーク・DB・テストツールに固有の再利用可能な作業方法 | 採用の決定、版の決定、プロジェクト固有のコマンドや秘密情報 |
| プロジェクト文書 | 採用技術と版、対象component、環境、repo・Git運用、正本所在、テストコマンド、制約、連携契約 | 再利用できる作業アルゴリズムの重複 |
| プロジェクトSkill（`<project>-adapter`） | 文書からだけでは再現しづらい固有の作業順序、複数正本・環境の照合、引継ぎの手続き | 技術スタックの固定リスト、Gitホスティング固有処理の共通化 |

Adapterが不要なプロジェクトでは配置しない。技術Skillも導入対象の採用技術とWork範囲に一致するものだけを配置・選択する。

## 技術採用情報の所在

開始時にプロジェクトの必読・入口文書から、対象componentの技術構成文書を辿る。例えばリポジトリ内の`Docs/Constraints/技術構成.md`、または指定された外部正本を使用する。ファイル名を全プロジェクトへ強制しない。

技術構成文書では、少なくとも次の情報が確認できるようにする。未決定なら未決定と記す。

- 対象component・repo・ディレクトリ／範囲。
- 採用言語、runtime、framework、DB、ビルド・テスト系。バージョンが規範として指定されていればその版。
- 開発・本番の制約、実行・検証コマンドの所在、必要な外部サービス、仕様正本への入口。
- Git remoteのホスト／レビュー方式／CI提供元、baseと統合先・ブランチ規則の参照先。秘密値は記載しない。
- 必要に応じて適用する`tech-*` Skillの識別子と、既存文書・lockfile・manifestの参照先。

既存の技術構成文書にこれらがあれば、新しい同内容の正本を作らずにその文書を利用する。実際のmanifest/lockfileやGit remoteの取得値は、現在の実装・環境の証拠であり、未承認の仕様変更ではない。

## Skill選択の契約

1. 対象Workのcomponentと関与するPI/テスト境界を定め、現行の技術構成文書と実際のrepoを確認する。
2. 共通SkillはWorkの局面で選ぶ。技術Skillは「文書上の採用が確認できる」「対象Workでその能力を使う」「利用可能なSkillのdescriptionが合う」の三条件で選ぶ。
3. 複数技術をまたぐWorkは必要なSkillを合成し、入力・出力境界とoracleを共通CAT契約で結ぶ。例: UI Skill＋E2E Skill＋DB Skill。全技術Skillを一律にはロードしない。
4. 技術Skillに書いたサンプルコマンドや一般慣行が、プロジェクト正本・現行manifest・制約に反するときは適用しない。採用技術が未確定ならSkillから逆算して決定しない。
5. 利用可能な技術Skillが無い場合は、共通Skillの役割・仕様根拠を維持したまま、対象技術の公式資料・現行プロジェクト設定を確認する。再利用が必要になった時点で新しい`tech-<technology>`を独立作成する。
6. `tech-*`はプロジェクト固有のブランチ規則・正本参照・承認者を変更しない。`<project>-adapter`は汎用技術手順を再定義しない。

## Gitとホスティング

GitリポジトリであることをCycleの前提とする。`git status`、commit、branch、worktree、diff、remoteの確認は共通契約。GitHub・GitLab・Bitbucket・セルフホスト等はプロジェクト文書または実際のremoteで確認し、GitHub固有のIssue/PR/Actions APIを必須にしない。コードレビュー機構の名称は利用先に応じてPR・MR等に置き換える。forgeのAPIが無ければGit操作と確認可能な証拠を使い、レビュー・CI・マージの未確認状態を成功と扱わない。

VS Code/Copilotが読む`.github/agents`や`.github/skills`は**ワークスペース内の設定ディレクトリ名**であり、GitのremoteがGitHubであることを要求しない。Copilot自体とGitHubというGitホスティングサービスも区別する。

## Project Adapterの設置判断

静的なルール・技術表・ブランチ方針・正本URL・テスト実行コマンドは文書側に置く。プロジェクト独自の「この入口から正本を辿り、変更後に同じ正本へ再取得を行う」「複数repoの実状態を照合する」のような**再現性ある手順**が残る場合だけ`<project>-adapter`を作る。descriptionに対象プロジェクト名と発動局面を明記し、共通Skillは自動的にそのAdapterを前提にしない。XPlayServer向けは`extensions/xplayserver-adapter/`にSkillと接続マップをまとめ、`--adapter xplayserver-adapter`を明示した場合だけ導入する。


## 決定論的な導入・検査の選択

採用済み技術はWorkの`technologies`へ規範技術文書に基づいて記載し、`cat_flow.py route`で共通Agentと対応Skillを抽出する。`cat_install.py`はこのリストだけから`.github/skills`の採用対象を決め、無関係なSkillは配置しない。実際のSkill自動選択はVS Code/Copilot上で別検証する。`cat_flow.py git`はローカルGitの差分とブランチ制約の実測のみを扱い、GitHub以外のremote・PR/MRプロバイダにも矛盾しない。実体がローカルに無ければ`not-run`を返す。

## 適用前確認

既存リポジトリへ通常Workを投入する前に、導入後の参照解決、コンポーネント単位のSkill選択、変更可能範囲を確認する。`cat_install.py`は静的な参照解決と選択外Skill/extensionの非配置を検査するが、`cat_flow.py route`の結果も実際の対象componentと照合する。

XPlayServerのGoogle Drive正本接続・更新後再取得は明示導入した`xplayserver-adapter`の手順であるが、VS Code/Copilot上の認証・取得・再開は未実証。現行正本・現行Git・実環境の三者を混同せず、未取得の場合は確認済みとしてWorkを進めない。
