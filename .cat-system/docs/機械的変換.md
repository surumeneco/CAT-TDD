# 機械的変換：人間可読正本から型付きIRへ

## 位置付け

CAT理論の `Process / PI / TCE / DomainRule → TestModel → テスト選択 → テストコード` を独立した変換段階として扱う。理論正本は `forGPT/SystemDevelopment/00_理論・構想/設計理論.md` であり、本書は試作コンパイラの実行契約である。

現行の標準経路は次の通り。

~~~text
CAT Markdown (semantic_contract: markdown-v2)
  ↓ deterministic parse / type check / language normalization
normalized cat-machine/v2 IR (memory / optional cache)
  ↓ symbolic compilation
TestModel.md (cat-test-model/v2)
  ↓ concrete vector selection + binding
Test code
~~~

JSON IRは変換器内部のデータ構造であり、意味の正本ではない。人間が同じ仕様をMarkdownとJSONへ二重入力する工程を設けない。

## 意味の出典

`markdown-v2`では、Markdownの人間向け構造が形式意味の出典である。日本語/英語の見出し・column・Domain・式keywordは同じIRへ正規化する。具体的記法は[Artifact記法](Artifact記法.md)を正とする。

互換入力:

- `markdown-v1`: 旧 `Contract / Fields / Rules / Effects` 形式。
- `machine-only`: 旧 `cat-machine` JSON authority。

一回のcompileではsemantic contractを混在させず、意味権威を一意にする。

生成TestModelは `markdown-v2` なら `semantic_authority: cat-markdown/v2`、旧v1なら `cat-markdown/v1`、machine-onlyなら `cat-machine/v2` を記録する。Markdown系は `normalized_ir: cat-machine/v2` を記録する。

## `markdown-v2`からIRへの写像

### Process

人間向け:

- `Contract / 契約`
- `Interfaces / 境界`
- `State / 仕様状態`
- `Observations / 観測能力`
- `Actions / 作用能力`
- `Triggers / 起点`

内部では、PI受信項目に加えてProcess stateを `role=state`、明示観測能力を `role=observation`、明示作用能力を `role=action` として型付き意味要素へ正規化する。

### PI

`Boundary / 境界` で相手ProcessとPI全体の方向を保持する。`Fields / 項目` の `receive / 受信` は内部 `input`、`send / 送信` は内部 `output` へ正規化する。Process内部stateはPIへ入れない。

Presenceは意味として保持する。現行決定論コンパイラが扱えるのは `required / 必須` のみであり、optional/absent/undefinedをrequiredへ縮約して通さない。

`Operations / 操作` の受付操作はProcess Triggerとの参照整合を検査する。

### TCE

人間向け正本は `Behaviors / 振る舞い` の一表とする。

~~~text
ID + Trigger + Condition + Outcome + Effects
↓
rule(id, trigger, when, allowed[outcome].write[])
~~~

Effectsは `target = expression` を `;` で複数記述できる。これは命令文ではなく、成立すべき仕様結果を表す。

旧v1の `Rules / Effects` 二表形式は互換parserだけが扱う。

### DomainRule

`Definitions / 定義` を名前付き限定式へ正規化する。日本語identifierを含むUnicode identifierを使用できる。

### CommonRule / DomainSpec

これらは正式Semantic Artifactだが、現行 `cat_compile_v2.py model` の局所symbolic compiler対象には含めない。lintとtraceabilityの対象として保持し、対象Workで必要ならAI作成TestModel・専用検証・独立レビューへ接続する。

非対応を理由に内容をPI/TCEへ無理に縮約しない。

## 限定式の正規化

式パーサは任意コードを実行しない。参照、literal、論理演算、比較、整数算術、限定組込み関数、DomainRule呼出しだけをASTへ変換する。

日本語alias例:

- `真 / 偽 / なし` → boolean/null literal
- `かつ / または` → logical and/or
- `否定(x)` → logical not
- `長さ(x)` → length
- `整数化(x)` → to-int
- `連結(a,b)` → concat
- `集合追加 / 集合削除` → set operations

文字列literal内部は変換しない。未許可構文、未知参照、型不一致、未証明enum Effect等は `BLOCKED` とする。

## Capability検査

`markdown-v2`ではConditionとEffectの参照可能範囲を次のように扱う。

~~~text
Condition readable
= PI receive fields
+ Process State
+ declared Observations

Effect writable
= PI send fields
+ Process State
+ declared Actions
~~~

未宣言ObservationをConditionから読む、または未宣言output/state/actionへEffectを書く場合はBLOCKする。

明示Observation/Actionを含むTestModel生成は可能だが、現行の汎用test-code bindingはその環境注入・観測方式を持たない。この場合はテストコード生成だけをBLOCKし、TestModelの意味を破棄しない。

## Coverage requirementとverification

TCEの `Coverage requirement / 網羅要求` は仕様要求であり、検証結果ではない。

現行compilerはenum/boolの有限guardを65536組以下で列挙できる場合のみ未被覆・重複・到達不能を検査する。

- `proved`: 機械的に閉包を確認できた。
- `uncovered`: 未被覆領域が見つかった。
- `unproven`: 非有限Domain等により本変換器では証明できない。

`closed`要求に対して全Triggerが `proved` でなければ、**normative compileはBLOCKする**。`--allow-draft`を明示した調査・草案生成では `uncovered / unproven` をTestModelへ保持できるが、そのTestModelのstatusは`draft`であり、`Coverage requirement: closed` と書いただけで検証済みへ昇格させない。

## TestModel

人間向け標準出力はMarkdownである。

~~~bash
python scripts/cat_compile_v2.py model Process.md PI.md TCE.md -o TestModel.md
~~~

`language: ja` のTCEを入力した場合、日本語見出し・column・式aliasでTestModelを出力する。内部IRの意味は言語によって変化しない。

TestModelでは次を分離する。

- Coverage requirement
- Coverage verification
- Rules / Effectsの内部正規化表示
- Derived frame conditions

Rules/Effects表は**派生TestModelの内部意味表示**として利用してよいが、人間が編集するTCE正本の記法ではない。

`.json`出力はdebug・互換・機械連携用。モデルからテストを生成するときは元CAT Artifactを再コンパイルし、指定TestModelが現行ソースと一致することを要求する。

## テスト具体値とbinding

具体値はTestModelの後段に置く。`vectors.json`は入力・初期state等の具体値選択であり期待結果を持たない。`binding.json`は技術driverへの接続情報でありCAT意味仕様ではない。

~~~bash
python scripts/cat_compile_v2.py tests TestModel.md vectors.json binding.json \
  --process Process.md --pi PI.md --tce TCE.md \
  -o generated.spec.ts
~~~

Observation / Action capabilityを含むモデルについて、汎用bindingに対応能力がない場合はtest-code生成をBLOCKする。特定framework向けの都合をSemantic Artifactへ逆流させない。

## CLIとWork

`cat_flow.py`は `Work.md` を内部 `cat-work/v1`へ正規化する。Work本文では日本語/英語見出し・column・Gate status aliasを受理するが、front matter keyと内部schemaは英語固定とする。

`compile`のファイル参照はWork/Workspace/宣言repoを基準に解決する。無印相対パスと`@work/`はWorkディレクトリから外へ出られない境界、`@workspace/`はproject root、`@repo:<name>/`は宣言repo、`@package/`はCAT packageを指す。

`--allow-draft`は試験・調査時だけ明示する。`--check`は生成物一致確認であり、意味承認、Red/Green、CI、merge、deploy、実使用確認を代替しない。

本変換器は開発環境の一機能である。機械可読範囲外ではAgentによる仕様/TestModel作成と独立レビューへ戻り、非対応領域を勝手に有限な別問題へ縮小しない。
