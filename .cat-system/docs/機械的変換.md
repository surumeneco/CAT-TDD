# 機械的変換

## 境界

決定論的に同じ入力から同じ出力を得られる処理はScript / Compiler / Validatorへ置く。AIは意味判断・設計・production implementationなど、機械変換で代替できない処理に限定する。

## CAT source → TestModel

~~~text
confirmed Process / PI / TCE / DomainRule
  ↓ cat_compile_v2.py model
TestModel.md
  + source_sha256
  + source_semantic_map
  + coverage verification
~~~

normative compileはconfirmed sourceと、対応可能なclosed-world検証を要求する。unsupported / uncovered / unprovenをAIで埋めない。CommonRule / DomainSpecが対象仕様として宣言され、現在のcompilerまたは専用deterministic verifierへ未写像ならnormative pathを`blocked`にする。`--allow-draft`はcompiler開発・shadow用途に限定する。

`model-conformance`は現在sourceからTestModelを再生成し完全一致を検査する。sourceとmodelが不一致ならstale/failedであり、TestModelを手修正しない。

## TestModel → TDD Execution Queue

~~~text
confirmed TestModel + vectors
  ↓ cat_compile_v2.py queue
TDD/Queue.json
~~~

Queue schemaは`cat-tdd-queue/v1`。各itemは次だけを持つ。

- `id`
- `model_ref`
- `vector_ref`
- `order`
- `status: pending | current | done | blocked`
- `evidence_ref`

Scenario、Expected Result、Oracle、Condition、Effect、input/output値はQueueへ置かない。`scripts/cat_queue.py`がstateを機械遷移させ、currentは最大1件とする。

## current item → executable test

~~~text
TestModel + vectors + Queue(current=1) + technology binding
  ↓ cat_compile_v2.py tests --queue ...
generated current test
~~~

normative test generationはQueueを必須とし、current vectorだけをrendererへ渡す。一度にpending全件のexecutable testを新規生成しない。

rendererが対象技術を表現できない場合、AIがtest本文を書いて回避せず、binding / renderer改善Workへ分離する。

## Red / Green evidence

`cat_flow.py run --id ... --execute`が宣言済みcommandだけを実行する。

Redでは対象test failureを機械取得する。失敗理由をsignature等で確定できない時だけ`inconclusive`として`tdd-checker`へ渡す。Green / regressionのpass/fail集約にReviewer Agentは不要。

execution evidenceはcommand context、input/output hash、JUnit hash等へ結び付ける。入力変更後のevidenceはstale。

## CAT conformance

`cat_flow.py conformance --kind process-closure|model-conformance|implementation-conformance`を使用する。

- process-closure: 現行compilerが証明可能な単一Process有限領域を機械判定する。ただしTCEの網羅要求が`partial`なら、その局所結果だけでProcess全体をclosedとは扱わず`inconclusive`とする。multi-Process composition等もinconclusive。
- model-conformance: sourceからの完全再生成一致を判定する。
- implementation-conformance: `cat-implementation-obligations/v1`をcategory別に集約する。各obligationは`source_ref`と検証`method`を必須とし、passed/failedはevidence、not-run/inconclusiveはreasonを保持する。failedはblocked、not-run/inconclusiveはinconclusive。

各conformance実行は `.cat-flow/conformance/<gate>.json` に入力hash・Work context・verdictをScript所有の証拠として保存する。`status`はこの証拠を再検証し、Work本文の自己申告だけでCAT適合性Gateをpassにしない。inconclusiveだけを対応Reviewerへ委譲し、そのReview evidenceで閉じることができる。failed / blocked / stale / not-runをReviewerでpassへ上書きしない。

## Scope ordering

`scripts/cat_scope_order.py`はWorkの`parent / depends_on`だけを入力としてcycle、dependency readiness、depthを計算し、ready集合のうち最深scopeを返す。依存関係そのものの意味はAI/仕様側が与える。

## Write guard

Agentがlocal repositoryへ書くstageでは、実行前後に`cat_flow.py guard --stage ... --phase start|finish`を使用できる。Workのrepository production write set外の差分があればblockedとする。guard evidenceをAgent自身の自己申告へ置き換えない。

## Structured handoff

`cat_flow.py handoff --stage ...`はWork ID、flow/stage、executor、permissions、source hash、current Queue item、unresolved decision、evidence refs、stale inputs、next permitted actionをJSONで返す。自由文handoffを再読用正本にしない。
