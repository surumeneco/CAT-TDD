# 機械的変換

## 境界

決定論的に同じ入力から同じ出力を得られる処理はScript / Compiler / Validatorへ置く。AIは意味判断・設計・production implementationなど、機械変換で代替できない処理に限定する。

### Effectの型包含に関する限定的な規則

型参照が示す意味をCompilerが推測してはならない。ただし、Effectが**他の宣言済みフィールドへの直接参照**であり、そのフィールドのDomainが出力先の`union<...>`の一構成要素と構造・出典を含めて完全一致する場合、その代入の局所型包含だけを許す。これは各選択肢の出現可能性や実装の外部作用を示さない。型定義が未解決ならModelは引き続きDraftで、名前が似ているだけの異なる参照、暗黙の変換、任意のunion包含は証明しない。

## CAT source → TestModel

~~~text
confirmed Process / PI / TCE[] / DomainRule
  ↓ assembled closure + cat_compile_v2.py model
TestModel.md
  + source_sha256
  + source_semantic_map
  + coverage verification
~~~

normative compileはconfirmed sourceと、対応可能なclosed-world検証を要求する。unsupported / uncovered / unprovenをAIで埋めない。CommonRule / DomainSpecが対象仕様として宣言され、Compilerで厳密な意味を証明できないときはnormative pathを`blocked`にする。限定された`cat:intrinsic-model/v1`の3種類の**出典承認済み構造述語**だけは、CompilerがソースSHA付きの`intrinsic_rule_proofs`を生成し、独立Model Conformanceがソースから再評価して証明内容を照合する。自由記述のVerificationや外部効果のrunner成功をこの規範証明に読み替えない。未解決Ruleが1件でも残るモデルは`draft`とし、`process-closure`を最終`passed`にしない。`--allow-draft`はcompiler開発・shadow用途に限定する。

有限ClosureのGuard直積が上限65,536組合せを超える場合、`--allow-draft --allow-partial`の診断ではTrigger単位の`coverage_checks`に`result: unproven`、`combination_count`、対象Guardを保持する。機械的に証明できなかったことを仕様矛盾やConfirmed Closureとみなさず、通常の規範Compiler/Process Closure Gateでは引き続き通過させない。

`model-conformance`は`cat_model_conformance.py`がcompiler本体の`load()`を再利用せず、confirmed sourceのTrigger / PI / Field / Rule / Allowed Outcome / frame condition / DomainRule inventoryを別経路で導出しTestModelと比較する。同一compilerの自己一致だけを適合性証拠にしない。sourceとmodelが不一致ならblockedであり、TestModelを手修正しない。さらに、JSON TestModelの`status: confirmed` / `coverage_requirement: closed`はProcess原本の`closed_world`が真であり、各Triggerに`proved`な局所Closure検査記録が存在し、未証明Presence・型・Interfaceがない場合のみ許容する。これはModel内の証拠の**出典整合性・内部整合性の検査**であり、有限状態の網羅を独立に再計算したという主張ではない。`process-closure`の正式Gateは引き続き別途必要である。

## TestModel → test vectors → TDD Execution Queue

~~~text
confirmed TestModel
  ↓ cat_compile_v2.py vectors --selection-rule rule-witness/v1
deterministic vectors
  ↓ cat_compile_v2.py queue
TDD/Queue.json
~~~

normative pathのvectorは手入力のTest Listではない。`rule-witness/v1`は、正確に列挙可能な有限input/state空間から各TestModel ruleの決定論的witnessを選ぶ。対象はboolean、enum、有限な整数区間、これらのnullable・union・required-only構造recordを含む（組合せ上限は65536）。実数、文字列、unbounded整数・sequence、有限である証明のないDomainや規定上限を超える集合には推測による代表値を選ばず、selectorはblocked、Process Closureはunprovenとする。ただし、非required入力のPresenceについても、明示された`is_missing`・`is_undefined`・`is_present`条件と有限な各状態を全て検査できた場合に限り局所Closureを証明する。非required出力は、単一の出典付き提供Operationが一意に定まり、各TCE結果のEffect/出力不在frameが`required`・`optional`・`absent`の状態制約と一致する場合に限り局所的な出力Presenceを証明する。`undefined`出力、複数提供操作の曖昧性、外部配送の真正性は引き続き未証明であり、実装のDriverと出力Operationの転送を合格済みと見なさない。Queue/test生成時にもvectorsを再生成して完全一致を要求し、TestModel ruleが1件でもvectorから欠落すればblockedとする。

Queue schemaは`cat-tdd-queue/v1`。各itemは次だけを持つ。

- `id`
- `model_ref`
- `vector_ref`
- `order`
- `status: pending | current | done | blocked`
- `evidence_ref`

Scenario、Expected Result、Oracle、Condition、Effect、input/output値はQueueへ置かない。`scripts/cat_queue.py`がstateを機械遷移させ、currentは最大1件とする。

## current item → executable test

~~~text
TestModel + vectors + Queue(current=1) + technology binding
  ↓ cat_compile_v2.py tests --queue ...
generated current test
~~~

TDD実装用のnormative test generationはQueueを必須とし、current vectorだけをrendererへ渡す。一度にpending全件のexecutable testを新規生成しない。

rendererが対象技術を表現できない場合、AIがtest本文を書いて回避せず、binding / renderer改善Workへ分離する。


## Confirmed仕様 → Test Suite同期（TDDとは独立）

既存実装のテスト整備は`scripts/cat_spec_test_sync.py`を利用する。Workは`flow: spec-test-sync`、`work_kind: test-maintenance`、Confirmed仕様・有効なdecision_refを持ち、Compilationに`process / pi / tce(s) / model / vectors / binding`を指定する。現在Workの`process-closure`と`model-conformance`がScript所有passed証拠であり、かつ再検査してstaleでない場合だけ同期を開始する。明示的な複数PIとDomainSpec型定義を全て入力・hash対象に含める。CommonRule/DomainSpecの規則は、承認済ソースの限定された`intrinsic_rule_proofs`が**全Rule IDを証明済**である場合に限り通過し、自由記述・外部作用・`allow_draft`から規範oracleを作らない。

~~~text
python .cat-system/scripts/cat_spec_test_sync.py plan --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py sync --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py verify --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py run --work Work.json --repo ./repo --repo-revision <HEAD> --check-id suite
python .cat-system/scripts/cat_spec_test_sync.py report --work Work.json --repo ./repo --repo-revision <HEAD>
~~~

テスト実行はWorkの`Checks`に`Stage: suite-run`、`Runner: junit`、対象全vectorの`Test IDs`、`@repo:<name>`のCWD、`{report}`へJUnit XMLを出力する実行argvを宣言し、`--check-id`で指定する。任意の未宣言コマンドを実行してGreenにすることはできない。

コマンド例のWorkとrepoは実体に置き換える。`plan`は読み取り専用。`sync`は生成所有テストと`.cat-flow/test-suite-manifest.json`だけを書き、`verify`は入力・Manifest・現disk hashの一致を再検証する。`run`は指定されたproject runnerの終了状態を`test-execution-passed / test-execution-failed / test-execution-not-run`として`.cat-flow/evidence/test-suite-execution.json`へ記録し、`report`はManifest/HEADと突合する。同期成功とrunner成功は独立しており、RedをTDD Queueの進捗へ転記しない。

生成先は`tests/generated/`や`apps/<component>/tests/generated/`等のテスト専用名前空間に限定し、Workに宣言した対象repoと`allowed_paths`で書込み対象の全パスを検査する。

Manifest schemaは`cat-test-suite-manifest/v1`で、`inputs`（`source_sha256`, `model_sha256`, `vectors_sha256`, `selection_rule`, `renderer_version`, `binding_version`, `repo_revision`）と`entries`（生成テスト相対pathをキーとする`test_id`, `owner`, `file_sha256`, `source_sha256`, `model_sha256`, `vectors_sha256`, `renderer_version`, `binding_version`）を保持する。プランは`create / update / unchanged / retain / blocked`を決定論的に判断する。所有者が`generated`で、現disk hashと旧Manifestが一致する場合だけ更新し、手書き・無所有・ローカル変更済み・欠落・ID重複は停止する。既存非選択ファイルを自動削除しない。target pathとManifest pathのroot外脱出・symlinkは禁止する。

現行対応rendererはVitestであり、対応外技術はbinding/renderer改善Workへ分ける。TestModelとvectors自体は既存Compiler/Selectorの出力を利用し、生成器が独自の期待値を定義しない。 VitestのCAT `set`型は、状態および出力について構造値の深い同値を一対一に照合し、配列中の順序差を無視する。重複要素は集合として不適合とし、`sequence`や通常のRecord/Scalarの順序・値の厳密比較は維持する。要素をJavaScript標準の文字列化ソートに掛けて「集合の同値」を代用しない。

## Red / Green evidence

`cat_flow.py run --id ... --execute`が宣言済みcommandだけを実行する。

Redでは対象test failureを機械取得する。失敗理由をsignature等で確定できない時だけ`inconclusive`として`tdd-checker`へ渡す。Green / regressionのpass/fail集約にReviewer Agentは不要。Green evidenceには実行時のcurrent Queue item IDとQueue hashを保存し、`cat_flow.py queue-state --evidence ...`はその証拠が現在Queueと完全一致する場合だけcurrentをdone化する。

execution evidenceはcommand context、input/output hash、JUnit hash等へ結び付ける。入力変更後のevidenceはstale。

## Implementation obligations

`cat_flow.py obligations --work <Work.md>`はconfirmed assembled specificationから`cat-implementation-obligations/v1`の検査項目骨格を機械生成する。生成時点では各項目を`not-run`とし、AIが検証済み状態を捏造しない。Interface / Capability / Behavior / Invariant / Cross-process / Domain / implementation-constraintの各項目はsource_ref、verification method、limitationを持つ。`implementation-conformance`実行時はまずobligation skeletonをconfirmed sourceから再生成して完全一致を確認し、その後Queueのdone evidence、model-conformance、Technology Inspector等のScript/Provider証拠をAggregatorが評価する。評価済み結果は`.cat-flow/cache/implementation-obligations-evaluated.json`へScript所有で保存する。

非決定的なTCEの複数Allowed Outcomeでは、**各代替の発生を義務化しない**。`behavior.<rule>`のGreenは選択された入力で観測結果が許容集合に含まれたことだけを示す。Implementation Invariantは`invariant.<rule>.allowed-set`（`generated-test-allowed-set`）として**ルールごとに一件**作り、script-owned Greenと独立Model Conformanceがともにpassedのときだけ、選択された観測に対する集合包含をpassedとする。代替ごとのsource-to-model frame対応は`model_outcome_frames`へ出典付きメタ情報として保存し、独立の発生証拠・runtime義務としない。旧`generated-test-frame`はルール単位Greenだけでpassedにせず`inconclusive`とする。仕様に結果ごとの発生可能性保証が明記された場合は、別途規範とoutcome別の証拠契約を設ける。生成テストのGreenも全入力・全実行の正しさは保証しない。

技術固有InspectorはTechnology Skillが提供できる。TypeScriptでは`tech-typescript/scripts/cat_typescript_conformance.py`が公開exportとPI operation、既知のenvironment/network/filesystem/clock/random/timer使用とProcess Observation/Actionを照合する。検査不能な領域は`inconclusive`として残す。

### 複数Processの構造型とRecord内部Presenceの接続

Process合成の型包含判定では、閉じたRecordの各フィールドについて、値Domainの包含とPresenceの許容状態を**別々に照合**する。Presenceの状態集合は required={value}、optional={missing,value}、absent={missing}、undefined={undefined}。送り手が取り得る状態のすべてを受け手が許容し、値状態がある場合にそのDomainの包含まで証明できたときに限り、構造的にmatchedとする。

宣言されていないRecordキーは常にmissingとみなし、片側でキーが省略されていても受け手のoptional/absentが許容するなら証明できる。型参照が未解決・包含検査が不確定な場合はinconclusive、状態集合が非包含の場合はmismatchとする。Record内のnullableはnullの許容であり、missing/undefinedの許容と同一視しない。構造的matchedは**外部転送・実装・複数Process交錯の証明ではない**ため、これだけでProcess合成の最終CAT Gateをpassedにしない。

### 規範RuleのVerifier観測と独立証明の分離

`cat-verifier-result/v1`の`status: passed`は、登録されたrunnerが固定fixtureを読み取り、assertionと一致する観測JSONを返したことを意味するだけである。Verifier結果には`verification_scope: fixture-assertions-only`および別の`normative_status: inconclusive`を明示し、`process-closure`で**後者のみ**を未証明Ruleの規範判定へ使用する。fixture上の不一致もそれだけでは自由記述Ruleの反証ではなく、Ruleの意味的同値が独立に証明されない限り規範判定は未確定とする。CommonRule/DomainSpecの自由記述Requirementとassertionの**意味的同値は証明しない**。そのため、Rule義務を任意のrunner観測成功だけで`passed`へ昇格しない。

`cat-implementation-obligations/v1`は、正規Compilerが入力Artifactから作った限定的な`cat:intrinsic-model/v1`の構造証明とソースSHAを保存する。**最新の独立Model Conformanceがpassed**で、Rule ID・Artifact ID・SHAが完全一致する場合だけ、その構造述語に対応する`normative-rule`義務を局所的にpassedとする。これはModel自身の構造を証明するものであり、Discord/DOM/DB等の外部実装やrunnerの意味同値を保証しない。一般的な自然言語Ruleと外部観測だけの場合は`inconclusive`を維持し、全体`implementation-conformance`を根拠なく通過させない。

## CAT conformance

`cat_flow.py conformance --kind process-closure|model-conformance|implementation-conformance`を使用する。

- process-closure: 現行compilerが証明可能な単一Process有限領域を機械判定する。ただしTCEの網羅要求が`partial`なら、その局所結果だけでProcess全体をclosedとは扱わず`inconclusive`とする。multi-Process composition等もinconclusive。
- model-conformance: sourceからの完全再生成一致を判定する。
- implementation-conformance: deterministicに再生成一致した`cat-implementation-obligations/v1`をcategory別に集約する。各obligationは`source_ref / method / limitation`を必須とし、passed/failedはevidence、not-run/inconclusiveはreasonを保持する。failedはblocked、not-run/inconclusiveはinconclusive。

各conformance実行は `.cat-flow/conformance/<gate>.json` に入力hash・Work context・verdictをScript所有の証拠として保存する。`status`はこの証拠を再検証し、Work本文の自己申告だけでCAT適合性Gateをpassにしない。inconclusiveだけを対応Reviewerへ委譲し、そのReview evidenceで閉じることができる。failed / blocked / stale / not-runをReviewerでpassへ上書きしない。

## Scope ordering

`scripts/cat_scope_order.py`はWorkの`parent / depends_on`だけを入力としてcycle、dependency readiness、depthを計算し、ready集合のうち最深scopeを返す。Process closure側では同一Processに属する複数TCEをassembled inputとして合成し、個別TCEがpartialでも合成領域がclosedならpassできる。依存関係そのものの意味はAI/仕様側が与える。

## Write guard

書込みを持つAgent stageではwrite guardは任意ではない。`cat_flow.py handoff --stage ...`がpre snapshotを自動作成し、Agent終了後の`cat_flow.py guard --stage ... --phase finish`がpassedになるまで次stageへhandoffできない。write set外差分、禁止Artifact変更、pending/blocked guardのbaseline再作成を拒否する。標準`Lifecycle/Works`配置ではpre guard時にdeepest-readyも機械確認する。

Refactorではさらに`refactor-baseline`のpassed evidenceと現在source contextの一致をpre guardで再検証する。baseline後にsourceが変わっていればstaleとしてrefactor Agentを起動しない。

## Structured handoff

`cat_flow.py handoff --stage ...`はWork ID、flow/stage、executor、permissions、source hash、current Queue item、unresolved decision、evidence refs、stale inputs、next permitted actionをJSONで返す。自由文handoffを再読用正本にしない。

## Normative promotion

confirmed昇格は通常Agent/Reviewerの書込みではなく、明示されたnormative decisionを受け取る専用authority executor `scripts/cat_promote.py`がcandidate/draftを別のconfirmed配置へ移動しながら`status / decision_ref`を更新する。意味の決定そのものはこのScriptで行わない。
