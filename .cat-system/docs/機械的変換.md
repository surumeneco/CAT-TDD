# 機械的変換

## 境界

決定論的に同じ入力から同じ出力を得られる処理はScript / Compiler / Validatorへ置く。AIは意味判断・設計・production implementationなど、機械変換で代替できない処理に限定する。

### Effectの型包含に関する限定的な規則

型参照が示す意味をCompilerが推測してはならない。Effectの**直接参照**は、宣言された元・先のDomain全構造とPresenceを検査し、証明可能な型包含（有限Domain、入れ子Record、union等）だけを許す。型包含が判定不能な場合は未証明を維持し、単純な型名の一致・Pythonの`True == 1`・非有限値域の代表値で証明を代用しない。明示Literalは出力先Domainへ完全に所属する必要がある。実行時の外部作用や選択結果の発生可能性を証明したことにはならない。型参照が未解決ならModelは引き続きDraftとする。

### 名前付き型の依存診断（規範Gateではない）

`cat_named_type_diagnostic.py` は明示されたDomainSpecの `## 型定義 / ## Types` のみを読み、依存グラフを検査する。未定義名・循環参照・未解決構造を原因別に記録し、根となる型のID、元SourceのArtifact ID / SHA-256、フィールド上の参照経路（例：`企業編集要求 → Delta → JSON`）を追跡する。**`Delta` の宣言が存在するときに `JSON` の未宣言を「Deltaが欠落」と言い換えない。**

~~~sh
python .cat-system/scripts/cat_named_type_diagnostic.py \
  --process xplay \
  --domain-spec path/to/active.domain-spec.md \
  --domain-spec path/to/dependent.domain-spec.md \
  --allow-draft \
  --output diagnostics/type-resolution.json
~~~

`--allow-draft` は未承認候補の*調査のための読取許可*であり、通常は省略する。未承認候補Sourceを確認済みの規範入力へ変換しない。JSONの `status: diagnostic`、`formal_gate_status: not-run`、`all_resolved` は互いに別の状態である。CLIの終了コード0は診断の成功であり、`resolved_count` が `declared_count` に達した場合でも型のwire意味、日時精度、JSON深さ・禁止値、外部送受信、Rule／Process Closureの適合を証明しない。全依存が未解決のときも既存の正規Compilerの `blocked` 判定は変えない。

## CAT source → TestModel

~~~text
confirmed Process / PI / TCE[] / DomainRule
  ↓ assembled closure + cat_compile_v2.py model
TestModel.md
  + source_sha256
  + source_semantic_map
  + coverage verification
~~~

normative compileはconfirmed sourceと、対応可能なclosed-world検証を要求する。unsupported / uncovered / unprovenをAIで埋めない。CommonRule / DomainSpecが対象仕様として宣言され、Compilerで厳密な意味を証明できないときはnormative pathを`blocked`にする。限定された`cat:intrinsic-model/v1`の**出典承認済み限定構造述語**だけは、CompilerがソースSHA付きの`intrinsic_rule_proofs`を生成し、独立Model Conformanceがソースから再評価して証明内容を照合する。自由記述のVerificationや外部効果のrunner成功をこの規範証明に読み替えない。未解決Ruleが1件でも残るモデルは`draft`とし、`process-closure`を最終`passed`にしない。`--allow-draft`はcompiler開発・shadow用途に限定する。

CommonRule・DomainSpecのMarkdown規則表は、セル区切りの `\|` と1個のバックスラッシュを表す `\\` のみをエスケープとして解釈し、それ以外の `\d`・`\.`・Windowsパス等のバックスラッシュを規範Source文字列として保持する。消えたバックスラッシュによって別Processの完全IDへ書換わり、Ruleを`not-applicable`と誤判定してはならない。この字句保持だけでは自由文Ruleの意味は証明されない。 Markdown TestModelにも`Normative rule sources`／`規範Rule出典`と`Normative rule obligations`／`規範Rule義務`の表を生成し、Rule Source ID・種別・宣言元Process・SHA、Rule ID・元のCondition／Requirement／Verification contract・`unverified`／`not-applicable`／`intrinsic-proved`の区別・明示Scope証拠を残す。全Rule義務（適用内・適用外・自由文未証明を含む）は、参照先一覧のSHAに間接依存するだけでなく、個別に元Sourceの`source_sha256`と`source_kind`を保持する。独立Source→Model照合は元のRule Sourceから一致を検査し、単体Verifierも両属性が出典一覧と一致しない提出Model/Registryを拒否する。ただしこれはModel内の出典整合であり、規範Ruleの意味や実行Providerの真正性を保証しない。独立Markdown Source→Model Conformanceはこれらを元Sourceから照合し、一覧削除・対象Process／内容／証明状態の改竄を拒否する。Markdownは`Intrinsic rule proofs`／`内在Rule証明`表にも、**既に正規Compilerがソースから証明した**限定構造命題のRule ID・Source Artifact/SHA・対象命題・検証契約・証明方法・適用範囲・結果を完全に記録する。独立Source→Markdown Model Conformanceはこれを元Sourceから別経路で再計算し、証明書の削除・追加・重複・属性改竄・旧Source SHAを拒否する。これらは限定された構造命題の証明記録であり、自由文Ruleの意味的同値や外部Provider証明を与えない。 Markdown TestModelはこれに加え`Resolved named types`／`解決済み名前付き型`のJSON節に名前付きDomainの**解決後構造・宣言元Artifact・Source SHA**を記録し、`Operation presence`／`操作別Presence`表に各Operation・Field・Presence・所有PIを、`Observation availability`／`観測利用可能時点`表に観測ID・出典・Trigger別利用可能性を保持する。独立Source→Markdown Model Conformanceはこれらと`Fields`表のDomain表示をSourceから照合し、欠落・別操作へのPresence移植・未来観測への改竄・型構造のすり替えを拒否する。`PI operations`／`PI操作`表は操作ごとの所有PIを、`Fields`／`仕様要素`表はPIの入出力Fieldごとの**基本Presence・所有PI**をSourceと一致する値で保持する。Process自身のState／Observation／ActionはPI所有や基本Presenceを持たないため両列を`—`と記録する。独立Source→Markdown Model ConformanceはOperation所有PIとField基本Presence・所有PIを別々に照合し、欠落・別PIへの移植・Presence変更やProcess-owned Fieldの偽のPI帰属を拒否する。Operation別Presenceは基本Presenceの上書きであり、いずれか一方の表示で他方を代用しない。複数PIを組み立てるProcessの`PI boundaries`／`PI境界一覧`は、**全PIの出典Artifact・相手Process・方向・複数peerの明示リスト（JSON）**をSource単位で記載する。単一PI用の`PI boundary`表示やProcess全体のPI ID一覧だけで複数PIの境界関係を代用しない。独立Source→Markdown Model ConformanceはPIごとの境界を元Sourceと照合し、行欠落・相手PIの入れ替え・方向やpeerの改竄・重複を拒否する。旧Markdown Modelが当該列・節を持たない場合は再生成が必要である。独立Source→Markdown Model Conformanceは、出典Artifact・PI操作・Trigger・DomainRule定義・TCE Rule・Effect・導出Frameの重複行を正規化前に拒否する。辞書や集合への変換で重複を消し、元Sourceと異なる表を`passed`にしてはならない。これもSourceとModel間の意味保存であり、名前付き型の外部wire意味や実Provider真正性・到達可能状態の一般証明を追加するものではない。

**Guardの網羅**と**Effectの値域・全域性**は別の証明義務とする。Compilerは各TCEのEffectについて`effect_checks`（出典TCE ID/Rule ID/結果/書込先別）を作り、未証明項目を`unverified_effect_ids`へ記録する。直接参照のDomain包含、LiteralのDomain所属、実際に全入力の組合せを列挙できる式（現行上限4,096）に加え、宣言Domainの**整数加算区間包含**と**型付き集合への要素追加**の厳密な閉包性だけを`typed-domain-closure/v1`として証明できる。非required入力をEffectが読む場合は、当該TCE Guardの評価順序を考慮して`is_present`が**必ずその入力の存在を保証する場合だけ**所属証明に進む。Guardの別分岐・別入力・Presence検査より先の危険な参照は根拠にしない。型未解決・根拠のない非required入力・出力等の利用不能な参照・対応外の非有限演算・上限超・値域外出力は理由付きで`unproven`とし、Guardが`proved`でもEffect未証明のModelは`draft`のままとする。Guardの直接列挙上限65,536・後述の厳密な因数分解予算とEffect式の全列挙上限4,096は別物であり、外部Driverや実行時副作用を証明しない。独立Model Conformanceは元のProcess/PI/TCEからEffect証明対象を再構築し、欠落・改ざん・虚偽のConfirmedを拒否する。Markdown TestModelに未証明Effectの証拠を表現できない場合、独立照合はその規範的主張を受理しない。

一般の有限ClosureのGuard直積が直接列挙上限65,536組合せを超え、厳密な因数分解・真偽分割でも予算内に証明できない場合、`--allow-draft --allow-partial`の診断ではTrigger単位の`coverage_checks`に`result: unproven`、`combination_count`、対象Guardを保持する。ただし、次の限定的な**Guard真偽分割と述語の因数分解**は元の値の全列挙を必要としない。機械的に証明できなかったことを仕様矛盾やConfirmed Closureとみなさず、通常の規範Compiler/Process Closure Gateでは引き続き通過させない。

厳密な有限Domainまたは真偽同値類が既に成立している場合、各述語のAST依存軸を使って真理値をメモ化し、直接列挙上限を超える直積も正確に走査する。上限は200万セル、1述語表65,536組、全述語表100万組、6,400万参照。巨大な論理結合は `and/or/not` のみ評価順・短絡を保存して分割する。 行走査の参照予算で証明できない場合、既に正当化された同じ最大200万分類をビット位置へ写し、各原子述語の依存軸の全評価（1原子65,536、合計100万まで）を共有し、`and/or/not` の真・未定義領域を順序付き短絡で正確に合成する有限mask経路を用いる。maskの演算量（6,400万64-bit word相当）と論理保持容量（64MiB相当）も有界とし、枯渇時は未証明。制約で許容された領域の未定義・空の許容領域・Guard重複・未被覆を合格にせず、反例は元の直積順で復元する。独立Source監査はCompilerのmaskやreceiptを受け取らず、独自に導出したSource AST・分割から同じ純粋な述語評価プリミティブを実行して結果・反例を比較する。決定論的Vectorは許容領域の各Ruleの最初の具体witnessを元の式でも再確認する。未観測の存在代表値を値として読む近似はこの経路では受理しない。予算超過は未証明で、仕様違反とは区別する。独立Source監査も同じ有効領域から別に真偽を再計算する。無限値域の具体件数は引き続き `null` とし、Vector選択の上限は別に扱う。

**`integer-literal-partition/v1`**：`required`な整数PI入力または整数state/observationが、`eq/ne/lt/le/gt/ge`による**整数リテラルとの直接比較**のみに現れ、式が`and/or/not`で組合わされている場合、各定数の前後・定数点を整数値域に制限して代表元を列挙する。各分割区間内で全比較の真偽が不変であるため、この分割の直積が上限65,536以下なら当該Guardの局所網羅/重複を**正確に**証明できる。元の値域が無限であっても等価類の完全性を使うので、任意の有限サンプルによる推測とは異なる。証拠は`coverage_checks`の`proof_method`、`partition_fields`、`abstract_state_count`、`proof_scope`で明示し、無限集合の**実数**を`uncovered_count`/`overlap_count`として報告せず`null`に保つ。比較以外の整数演算、**下記の限定された2〜5参照整数比較以外の**他fieldとの比較、DomainRule呼出、名前付き/Record/後述の限定契約以外のPresence未対応、直積上限超は安全側の`unproven`である。PI制約も同じ対応範囲に含み、元Sourceからの独立Model Conformanceが別実装で同じ分割と証拠値を再計算する。Rule/Effect値域/外部作用の証明に転用しない。

**`string-literal-equality-partition/v1`**：`required`な**制約なしの`string` Domain**を持つPI入力またはstate/observationが、文字列定数との直接の`==`/`!=`にのみ現れ、それらの条件を`and/or/not`で結合する場合、出現した各定数と**それ以外の全文字列**を厳密な真偽同値類として扱う。後者の代表文字列は使用された定数と衝突しないよう決定論的に選ぶ。この同値類の**全域性を述語の構造で証明**できる場合のみGuard Closureを`proved`にでき、その他クラスの具体値を無作為に試して推測したものではない。整数分割と混在するときの証拠名は`integer-string-literal-partition/v1`。文字列の加工やfield間比較、format付き文字列、DomainRuleの不透明な呼出し、後述の限定契約を除く非required Presence、組合せ上限超は証明対象外。独立Model Conformanceはソースからこの分割を再計算し、改竄した`coverage_checks`を拒否する。PI制約・Guardの局所証明に限り、Effect・Rule・外部作用の全域性は含まない。

**`required-record-member-partition/v1`**：型付き`member` IRは、親required input recordとmember名を分離し、Guard・Effect評価では親の値を実際に射影する。Guardが親record全体を観測せず、宣言されたrequired scalar memberの参照に限定される場合、証明用の一時的なmember座標に射影し、既存の有限列挙・整数参照順序／定数分割・実数定数順序分割・文字列定数分割を適用する。最大5個の制約なし文字列参照の直接等値／不等値比較は定数と相互等値類を保つ代表値で全真理値を被覆する。未観測memberはGuardの真理値に影響しないため合法な具体値を1つ選び、未観測optional/absent memberは省略する。非対応型／undefined／全record読取りとの混在／DomainRule呼出し／直接列挙・因数分解予算超過等で証明不能なら`unproven`（厳密有限列挙可能な場合は既存経路）を維持する。独立Source監査は元PI・TCEからmemberを別途束縛し、同じ真理値類を再構成し、JSONでは表示文字列だけでなく射影式のASTも照合する。生成Vector・テストコードには元のrecordのみを渡し、一時座標をwireへ露出させない。この局所証明は到達性・一般関係／実装全域の証明ではない。

**`real-literal-order-partition/v1`**：必須の`real` PI入力またはreal state/observationについて、有限の整数・実数定数との直接の大小比較（`lt/le/gt/ge`）とBoolean結合だけから、Domain上下限と全比較境界を用いて点・開区間・非有界端の真理値一定な領域を厳密に構成する。境界は正確な有理数比較で扱い、各領域に実行時のDomainに属する具体値を確定できない場合は`unproven`とする。全具体値の有限列挙や数値近似による閉包推定ではない。CATの型区別付き等値、実数同士の参照比較（次の限定契約を除く）、算術式、optional real、未宣言到達性はこの述語断片に含めない。独立Source→Model照合は元Sourceから領域分割・被覆を再構成する。Vectorは同じ述語断片の具体witnessを決定するが、外部Effectや全域実装正当性の証明ではない。

**`real-reference-order-partition/v1`**：2〜3個の必須real参照について、相互および有限数値定数との直接大小比較（`lt/le/gt/ge`）のBoolean結合を対象とする。全Domain上下限・定数を共通の有理数境界として固定し、各開領域に参照数と同じ数の相異なる順序付き実行可能代表値を確定する。同一領域内の値の全弱順序を保存できるため、各Domainへの包含と全比較の真偽を保持する。実行可能な代表値不足・65,536組超過・算術・型区別付き等値・optional／未解決型等は`unproven`とする。独立Source監査とVector生成も共通境界・順序保存の契約を検査する。これは局所Guard証明であり到達性や外部Effectを証明しない。

**`two-reference-linear-order-partition/v1`**：相異なる2個のrequired scalar参照（両方integerまたは両方real）の同一の直接加算または減算 `a+b` / `a-b` と整数定数との大小比較（`lt/le/gt/ge`）、およびそのBoolean結合を対象とする。整数または未指定のDomain上下限から和・差の像の上下限を厳密に導出し、全定数境界・開区間・非有界端に対する合法な原像を構成する。real値は受け取った有限数値の正確な値として比較し、中間の和・差をbinary64へ丸めたり巨大整数をfloatへ強制変換したりしない。原像の実行可能な代表値を確定できない場合、同一参照の別式・直接比較・未知の呼出し・型区別付き等値・fractional Domain境界・非required Presence・組合せ上限超は`unproven`。既存の一般算術Effect値の評価は変更しない。独立Source監査も像の境界と原像を再構成し、Vectorは合法な具体値を用いる。全域到達性や一般算術solverを意味しない。

**`string-reference-equality-partition/v1`**：2〜5個のrequiredな制約なし`string`参照の直接等値・不等値と文字列リテラル比較を対象とする。全リテラルを固定し、参照数と同じ数の互いに異なる未使用文字列を加えれば、任意の文字列の等値パターンを代表できる。独立Source検査も同じ完全な等値類を再構成する。型付きformat、加工・opaque call、非required参照、組合せ上限超は対象外であり、特定IDのサンプリングではない。

**`optional-integer-literal-partition/v1` / `optional-string-literal-equality-partition/v1`**：上記の整数・文字列のリテラル比較に加え、同じPI入力に対する明示的なPresence述語を許す。Operationで実効`optional`となる入力は、全present値の厳密な真偽類にmissingの1類を加える。missingで通常値を読んだ場合は短絡評価を含む実式の評価で`unproven`とし、暗黙default・undefined・nullへの変換はしない。宣言済みPI制約も同じ分割で検査し、空有効領域、欠落、重複、未到達を検出する。独立Source監査・Vector生成も同じPresenceを保持する。値の加工、他fieldとの比較、format付き文字列、関数呼出しはこの証明の対象外。

**`integer-reference-equality-partition/v1` / `integer-reference-order-partition/v1`**：同一の`integer` Domain（下限・上限は任意、ただし**少なくとも2整数値を持つ**）を持つ**二つのrequired参照**が、互いの直接の比較`==`／`!=`／`<`／`<=`／`>`／`>=`以外ではGuardとPI制約に現れず、それらを`and/or/not`で合成する場合、隣接値`L,L+1`を各参照に割り当てた4組で**小なり・等しい・大なり**の3真偽同値類を厳密に検査する。`L`と`L+1`は共通Domainの内部に固定する。この3関係以外をSourceが区別しないことを構文で確認するため、無限Domainについても無作為標本による推測ではない。等号・不等号だけのときは既存証拠名`integer-reference-equality-partition/v1`、大小比較を含むときは`integer-reference-order-partition/v1`と区別する。Compilerと独立Source→Modelの各計算は元Sourceの述語から分割・Guardを再評価し、Vectorも同じ意味上の分割域だけから実例を選ぶ。異なるDomain、算術、文字列等との異種比較、非required Presence、DomainRuleの不透明呼出し、他fieldの混在で未対応の形式は引き続き`unproven`、局所分割によって判明した未網羅・重複は`uncovered`／`conflict`であり、安易にClosure成功へ昇格しない。有限値域や他の厳密分割との混合証拠は`mixed-exact-predicate-partition/v1`。いずれも**初期状態からの一般到達可能性、Effect totality、自由文Rule意味同値、Provider真正性を証明しない**。
同一整数Domainの直接参照順序・等値分割は、有限Domain同士でも未分割直積が65,536組を超える場合に適用する。例えば0〜1439の日内分と予定分の大小・等号境界は全組列挙せず弱順序を保持する代表値で検証する。小さい有限直積の従来証拠は維持する。


**`integer-reference-equality-partition/v2` / `integer-reference-order-partition/v2`**：上記の2参照を**3〜5個のrequired整数参照**へ一般化する。すべて同じ連続整数Domainで、各参照の使用が相互の直接`eq/ne/lt/le/gt/ge`比較とその`and/or/not`合成のみである場合、参照の全弱順序（同値の束ね方と大小の順序）を厳密に代表する。N個の参照には共通Domain内の連続するN整数（有界DomainがN値未満ならその全値）を使い、各参照の値割当ての直積を評価する。これは任意の実際の値組を順序保存で代表値組へ写せるため、比較述語の真偽を変えない。評価する抽象組数は最大`5^5=3125`（他の有限Fieldとの積を含め65,536以内）とし、値域を恣意的に間引かない。**二つの参照のみの証拠は既存v1のまま**維持する。Compilerの局所Coverage、独立Source再導出、決定論的Vector、正規Process Closureで同じ適用範囲を使う。異Domain、算術・リテラルとの混合、非required Presence、未解釈呼出しや容量上限超は未証明のまま扱い、局所関係の真偽類を初期状態からの到達可能性・Effect・外部作用の証明に読み替えない。有限の狭いDomainでは従来の実値全列挙を優先し、取り得ない3値の全相異関係を発明しない。\n\n**`integer-reference-range-order-partition/v1`**：2〜3個のrequired整数参照の**Domainが互いに異なる**場合、または同一Domainで参照間比較と整数リテラル比較を混在させる場合にも、局所Guardの厳密真偽分割を行える。使用可能な原子述語は、二つの異なる整数参照間の直接`eq/ne/lt/le/gt/ge`、および整数参照と厳密な整数リテラルとの直接比較のみで、結合は`and/or/not`に限る。**必ず少なくとも一つの参照間比較を含む**ことと、各整数Domainが端点の任意性を許す連続整数区間であることを確認する。全参照のDomain下限・上限、式に現れる整数定数を境界として整数域を単一点と開区間に分割する。各開区間で最大N個（N=参照数）の連続代表値を選び、狭い有限区間では全値を選ぶ。どの元値組も、定数点の位置・Domain包含・各参照の大小／等号関係を変えずに代表組へ順序保存写像できるため、対応可能な全Guard真偽類を漏らさない。Compilerと独立Source監査はそれぞれ同じ条件を別実装で検査し、Sourceからの値域外代表値や、算術・非整数リテラル・非required Presence・不透明関数呼出しは証明しない。抽象直積が65,536を超えれば`unproven`に戻し、局所成功を初期到達性・Effect totality・外部Providerの証明に昇格しない。旧2参照v1、同Domain3〜5参照v2の証拠名と意味を維持する。\n\n`model-conformance`は`cat_model_conformance.py`がcompiler本体の`load()`を再利用せず、confirmed sourceのTrigger / PI / Field / Rule / Allowed Outcome / frame condition / DomainRule inventoryを別経路で導出しTestModelと比較する。同一compilerの自己一致だけを適合性証拠にしない。sourceとmodelが不一致ならblockedであり、TestModelを手修正しない。さらに、JSON TestModelの`status: confirmed` / `coverage_requirement: closed`はProcess原本の`closed_world`が真であり、各Triggerに`proved`な局所Closure検査記録が存在し、未証明Presence・型・Interfaceがない場合のみ許容する。さらに、独立Model Conformanceは元のProcess/PI/TCEのGuardとPI制約、Operation別Presenceから、上記の直接列挙・因数分解予算内の有限入力領域または厳密な整数リテラル区間・文字列リテラル同値類・限定整数2〜5参照および異Domain・定数混合の厳密な比較におけるGuard成立分割を**CompilerのCoverage receiptを使わずに再計算**する。元ソースに網羅漏れ・重複・到達不能・証明不能な非有限領域があるのに、TestModel側の`coverage_checks`や`status`を`proved`／`confirmed`へ書き換えた場合は`blocked`とする。有限分割の証拠にはGuard参照、未網羅・重複の件数と最大64/16件の具体例、未到達Rule ID、PI制約の有無も含め、部分的な数値・反例・到達性の書換えは同じく拒否する。これは有限Guard局所網羅とSource/Modelの整合性証明であって、自然言語Ruleの意味同値・外部Effect・実Driverの実行検証を代替せず、`process-closure`の正式Gateは引き続き別途必要である。

**PI制約の評価時点と人間可読Model**：PI制約の適用先は所有PIの受付OperationへSourceにより束縛されたTriggerに限る。提供結果を含む制約や対応受付Operationのない制約は受付Guardへ混入させず、`unbound_pi_constraints`に所有PI・元の式・未証明理由を残す。独立Model Conformanceは元PIから未束縛の義務を再導出し、モデルでの削除・理由変更・`status: confirmed`／`coverage_requirement: closed`への不当な昇格を拒否する。JSON TestModelは`pi_constraint_scopes`と`unbound_pi_constraints`を保持し、**Markdown TestModelも**`PI constraint bindings`／`PI制約の束縛`表に所有PI・適用Trigger・式・未証明理由を保持する。Markdownの式一覧だけを根拠に別OperationへPI制約を伝播させない。これらは宣言された式の所属と評価時点の表現・照合であり、将来の結果観測の真正性や結果関係の全証明を追加しない。 また、Markdown TestModelのfront matterで宣言する`schema`・`process`・`semantic_authority`・`language`と、`status`および`Coverage requirement`は本文の一致検査と独立の規範主張である。独立Model Conformanceは出典SourceのProcess・契約版・言語、元の有限Guard評価・未束縛PI制約、規範Rule/Effectの未証明状態から評価し、`draft`から`confirmed`または`partial`から`closed`への根拠なき改竄を拒否する。未対応のMarkdown証拠表が要求される場合は従来どおり未証明／`blocked`を維持し、Markdownのfront matter単独を正式Gateの合格証拠と見なさない。

## TestModel → test vectors → TDD Execution Queue

~~~text
confirmed TestModel
  ↓ cat_compile_v2.py vectors --selection-rule rule-witness/v1
deterministic vectors
  ↓ cat_compile_v2.py queue
TDD/Queue.json
~~~

normative pathのvectorは手入力のTest Listではない。`rule-witness/v1`は、正確に列挙可能な有限input/state空間から各TestModel ruleの決定論的witnessを選ぶ。対象はboolean、enum、有限な整数区間、これらのnullable・union・required-only構造recordを含む（直接列挙は65536組まで。それを超える場合は当該Triggerのsource-bound Guard coverageがprovedであり、上記の有限述語因数分解と同じ上限内で全組の実Guard/制約を再評価できる場合に限り選択する）。整数フィールドが上記`integer-literal-partition/v1`で真偽が不変な区間へ**完全に**分割できる場合、制約なしの文字列が`string-literal-equality-partition/v1`で比較定数とその他の全域へ**完全に**分割できる場合、または同一で少なくとも2値を持つ整数Domainの2参照が`integer-reference-equality-partition/v1`で等号／不等号の真理値類に**完全に**分割できる場合、元のCompilerと独立Model Conformanceが局所Closureを証明したうえで代表値からRule witnessを選択できる。Guardに現れない単純整数・制約なし文字列フィールドはwitnessを得るためだけに値域内の1値を選べるが、これをGuard/Effectの全域証明にしない。実数、**未対応の文字列比較・加工やformat付き文字列**、sequence、名前付き未対応、整数演算や比較に未知の意味が含まれるDomain、規定の証明・選択予算を超える組合せには推測による代表値を選ばず、selectorはblockedとする。Process Closureとvector選択の予算・対象値域は別であり、selectorの失敗を直ちにGuard未被覆と見なさない。ただし、非required入力のPresenceについても、明示された`is_missing`・`is_undefined`・`is_present`条件と有限な各状態を全て検査できた場合に限り局所Closureを証明する。PIで`required`と宣言された出力は、非required出力の有無や提供Operationの宣言の有無にかかわらず、対応Triggerの**すべてのTCE結果**が当該出力を生成することを必要とする。Guard網羅`proved`だけでは必須出力の生成を証明しない。独立Model Conformanceも元Process/PI/TCEを用いてこの義務を検算し、必須出力の欠落とその**未証明フィールドID**を再導出する。`confirmed`への偽昇格・空の`presence_unproven`・別のIDへの付替え・未存在ID・重複IDを拒否する。証明不能な入力Presenceを適切に未証明として保持したDraft Modelまで無条件に拒否しない。非required出力は、出典付き提供Operationが所有PIごとに一意に定まり（複数のPIが同一Triggerで提供する場合は全提供Operationが当該Triggerに明示的に束縛される）、各TCE結果のEffect/出力不在frameが`required`・`optional`・`absent`の状態制約と一致する場合に限り局所的な出力Presenceを証明する。`undefined`出力、同一PI内の複数提供操作の曖昧性、外部配送の真正性は引き続き未証明であり、実装のDriverと出力Operationの転送を合格済みと見なさない。決定論的vectorは所有PIごとに一意の提供Operationが確定した場合、単一なら`output_operation`、複数なら全Operation IDの集合を`output_operations`へ決定論的に保存する。複数は当該Triggerに明示束縛された異なるPIに限る。生成Vitestは`js-driver-provides/v1`の明示Bindingで同一Trigger実行の各操作の観測出力を全て検査し、state/output全体を単一の許容Outcomeへ照合する。単一の既存`js-driver-provide/v1`は維持し、複数への暗黙適用や操作identityの消去、別実行の結果合成を拒否する。局所閉包・vector選択はDriverの実在・実行成功を証明しない。非対応rendererの生成はblocked。Queue/test生成時にもvectorsを再生成して完全一致を要求し、TestModel ruleが1件でもvectorから欠落すればblockedとする。

`@cat:observed-transition-relation/v1` の証明済みTrigger-entry観測（boolean/enum）は、その明示された同一実行・PI・accept Operation・peerに束縛された場合に限り、`rule-witness/v1` の環境座標に加える。各vectorの `observations` は当該Triggerの証明済み観測IDと合法値を全て保持し、caller `input` とは分離する。証明済み `@cat:trigger-observation-relation/v1` の制約も選択・展開時に検査する。未証明・別Scope・観測値の欠落・制約違反を拒否する。これは具体テスト環境の条件であり、実装から取得した観測証拠ではない。Queueはこれを保持したvectorに束縛する。観測依存テストは明示 `observation_transport`（Vitest `js-driver-observed/v1`、JUnit `java-driver-observed/v1`）で生成できる。全宣言Observationが証明済みの有限Trigger-entry inventoryに属し、未対応Action能力がない場合に限定する。Driverの `prepareObservations(scope, values)` は出典付き観測条件を隔離された試験環境に設定し、`triggerObserved(operationIds, triggerId, input)` は**1回の論理Trigger実行**で取得した実際の `observations` と `output` を返す。生成テストは観測ID/値の完全一致を先に確認し、stateと出力全体を同じ許容Outcomeへ照合する。環境設定値の単なるechoを実観測にしない。Operation指定がある場合は両技術の明示的な複数Operation Bindingを併用し、outputをOperation→field recordとする。これらはテスト用の射影であり、製品内部の実行方式、実Providerの真正性・全実行の適合を証明しない。未対応観測・欠けたBindingはblocked。PI-only-unverifiedを観測依存oracleに用いない。

Queue schemaは`cat-tdd-queue/v1`。各itemは次だけを持つ。

- `id`
- `model_ref`
- `vector_ref`
- `order`
- `status: pending | current | done | blocked`
- `evidence_ref`

Scenario、Expected Result、Oracle、Condition、Effect、input/output値はQueueへ置かない。`scripts/cat_queue.py`がstateを機械遷移させ、currentは最大1件とする。 正規Queueの検証では、SHAで固定されたTestModel・Vectorsから**全ケース**の対応Ruleを再導出する。`id`と`vector_ref`は同一、`model_ref`はそのケースが指すTCE Ruleと一致、全Vectorは一度ずつ元の決定論的な順序（1からの整数`order`）で存在しなければならない。`pending`・`done`・`blocked`も例外ではない。正しいIDが存在するという集合包含だけでQueueの完全性・順序・oracle対応を証明しない。

TestModel + vectors + Queue(current=1) + technology binding

generated current test
~~~

TDD実装用のnormative test generationはQueueを必須とし、current vectorだけをrendererへ渡す。一度にpending全件のexecutable testを新規生成しない。

rendererが対象技術を表現できない場合、AIがtest本文を書いて回避せず、binding / renderer改善Workへ分離する。

## Confirmed仕様 → Test Suite同期（TDDとは独立）

既存実装のテスト整備は`scripts/cat_spec_test_sync.py`を利用する。Workは`flow: spec-test-sync`、`work_kind: test-maintenance`、Confirmed仕様・有効なdecision_refを持ち、Compilationに`process / pi / tce(s) / model / vectors / binding`を指定する。現在Workの`process-closure`と`model-conformance`がScript所有passed証拠であり、かつ再検査してstaleでない場合だけ同期を開始する。明示的な複数PIとDomainSpec型定義を全て入力・hash対象に含める。CommonRule/DomainSpecの規則は、承認済ソースの限定された`intrinsic_rule_proofs`が**全Rule IDを証明済**である場合に限り通過し、自由記述・外部作用・`allow_draft`から規範oracleを作らない。

~~~text
python .cat-system/scripts/cat_spec_test_sync.py plan --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py sync --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py verify --work Work.json --repo ./repo --repo-revision <HEAD>
python .cat-system/scripts/cat_spec_test_sync.py run --work Work.json --repo ./repo --repo-revision <HEAD> --check-id suite
python .cat-system/scripts/cat_spec_test_sync.py report --work Work.json --repo ./repo --repo-revision <HEAD>
~~~

テスト実行はWorkの`Checks`に`Stage: suite-run`、`Runner: junit`、対象全vectorの`Test IDs`、`@repo:<name>`のCWD、`{report}`へJUnit XMLを出力する実行argvを宣言し、`--check-id`で指定する。任意の未宣言コマンドを実行してGreenにすることはできない。

コマンド例のWorkとrepoは実体に置き換える。`plan`は読み取り専用。`sync`は生成所有テストと`.cat-flow/test-suite-manifest.json`だけを書き、`verify`は入力・Manifest・現disk hashの一致を再検証する。`run`は指定されたproject runnerの終了状態を`test-execution-passed / test-execution-failed / test-execution-not-run`として`.cat-flow/evidence/test-suite-execution.json`へ記録し、`report`はManifest/HEADと突合する。同期成功とrunner成功は独立しており、RedをTDD Queueの進捗へ転記しない。

生成先は`tests/generated/`や`apps/<component>/tests/generated/`等のテスト専用名前空間に限定し、Workに宣言した対象repoと`allowed_paths`で書込み対象の全パスを検査する。

Manifest schemaは`cat-test-suite-manifest/v1`で、`inputs`（`source_sha256`, `model_sha256`, `vectors_sha256`, `selection_rule`, `renderer_version`, `binding_version`, `repo_revision`）と`entries`（生成テスト相対pathをキーとする`test_id`, `owner`, `file_sha256`, `source_sha256`, `model_sha256`, `vectors_sha256`, `renderer_version`, `binding_version`）を保持する。プランは`create / update / unchanged / retain / blocked`を決定論的に判断する。所有者が`generated`で、現disk hashと旧Manifestが一致する場合だけ更新し、手書き・無所有・ローカル変更済み・欠落・ID重複は停止する。既存非選択ファイルを自動削除しない。target pathとManifest pathのroot外脱出・symlinkは禁止する。

spec-test-syncの現行対応rendererはVitestであり、TDD向けJUnit rendererとは独立である。対応外技術はbinding/renderer改善Workへ分ける。TestModelとvectors自体は既存Compiler/Selectorの出力を利用し、生成器が独自の期待値を定義しない。 VitestのCAT `set`型は、状態および出力について構造値の深い同値を一対一に照合し、配列中の順序差を無視する。重複要素は集合として不適合とし、`sequence`や通常のRecord/Scalarの順序・値の厳密比較は維持する。要素をJavaScript標準の文字列化ソートに掛けて「集合の同値」を代用しない。

## Red / Green evidence

`cat_flow.py run --id ... --execute`が宣言済みcommandだけを実行する。

Redでは対象test failureを機械取得する。失敗理由をsignature等で確定できない時だけ`inconclusive`として`tdd-checker`へ渡す。Green / regressionのpass/fail集約にReviewer Agentは不要。Green evidenceには実行時のcurrent Queue item IDとQueue hashを保存し、`cat_flow.py queue-state --evidence ...`はその証拠が現在Queueと完全一致する場合だけcurrentをdone化する。

execution evidenceはcommand context、input/output hash、JUnit hash等へ結び付ける。入力変更後のevidenceはstale。

## Implementation obligations

`cat_flow.py obligations --work <Work.md>`はconfirmed assembled specificationから`cat-implementation-obligations/v1`の検査項目骨格を機械生成する。生成時点では各項目を`not-run`とし、AIが検証済み状態を捏造しない。Interface / Capability / Behavior / Invariant / Cross-process / Domain / implementation-constraintの各項目はsource_ref、verification method、limitationを持つ。`implementation-conformance`実行時はまずobligation skeletonをconfirmed sourceから再生成して完全一致を確認し、その後Queueのdone evidence、model-conformance、Technology Inspector等のScript/Provider証拠をAggregatorが評価する。評価済み結果は`.cat-flow/cache/implementation-obligations-evaluated.json`へScript所有で保存する。

非決定的なTCEの複数Allowed Outcomeでは、**各代替の発生を義務化しない**。`behavior.<rule>`のGreenは選択された入力で観測結果が許容集合に含まれたことだけを示す。Implementation Invariantは`invariant.<rule>.allowed-set`（`generated-test-allowed-set`）として**ルールごとに一件**作り、script-owned Greenと独立Model Conformanceがともにpassedのときだけ、選択された観測に対する集合包含をpassedとする。代替ごとのsource-to-model frame対応は`model_outcome_frames`へ出典付きメタ情報として保存し、独立の発生証拠・runtime義務としない。旧`generated-test-frame`はルール単位Greenだけでpassedにせず`inconclusive`とする。仕様に結果ごとの発生可能性保証が明記された場合は、別途規範とoutcome別の証拠契約を設ける。生成テストのGreenも全入力・全実行の正しさは保証しない。

技術固有InspectorはTechnology Skillが提供できる。TypeScriptでは`tech-typescript/scripts/cat_typescript_conformance.py`が公開exportとPI operation、既知のenvironment/network/filesystem/clock/random/timer使用とProcess Observation/Actionを照合する。検査不能な領域は`inconclusive`として残す。

TypeScriptの限定能力検査 `typed-data-functions/v1` は、lockfile一致の実compiler ASTで明示Work production pathを検査する。通常の型付きデータと未改変標準intrinsicを前提とし、未知構文、外部参照、runtime import、入力書込み、未解析依存はinconclusive。compilerとsource/type dependencyのSHAを記録する。呼出元、proxy/getter、build transform、相手Processや全域挙動は対象外。

実装制約の独立検査には `Compilation.technology_constraints`（Markdownの `Technology constraints / 技術制約接続`）で `cat-project-typecheck/v1` を指定できる。JSONは `{"schema":"cat-project-typecheck/v1","repository":"Work内repo名","projects":[{"config":"tsconfig.json","compiler":"tsc"}]}`。複数packageにはそれぞれの設定を指定し、Vue SFCの検査には `vue-tsc` を用いる。`cat_project_typecheck.py` はWorkの `production_paths` から `.ts/.tsx/.mts/.cts/.vue` を列挙し、npm lockfileと一致する導入済みのcompilerで `--noEmit --showConfig` と `--noEmit --listFiles` を実行する。strict有効・型検査非無効化・成功終了・対象ソースの実ファイル一覧への包含を要求する。依存・設定・対象ファイルの欠落は未判定、compiler診断失敗はblocked。これは採用済みのstrictコンパイル制約に限定され、PI・能力閉集合・Vueの実行時reactivity・Process間通信・任意のlint規則を証明しない。JS出力はこの型検査の対象外。Work側の任意コマンドや自己申告の成功receiptは受理しない。Bindingと技術一覧はGateの入力ハッシュに含まれる。

`Vitest` と `Playwright` の採用テスト技術制約は、`cat_test_technology.py` による限定実行検査で扱う。Vitestは全done Queueの独立検証後、正規current-itemを再生成して実行時バイト列と照合し、Driver/Binding・宣言入力・Work/HEAD・実runner identity・named JUnit reportを検査する。Playwrightは同じcurrent-itemの実ブラウザ起動と対応する正常終了を観測する。純粋判定Driverの場合は既存Workのtest_pathsにある独立ブラウザ試験を `implementation-conformance` stage、`browser-` prefixのCheckとして宣言し、`node --test --test-reporter=junit --test-reporter-destination={report} --test-reporter=spec --test-reporter-destination=stdout <test>` を実行できる。実行証拠のない・不一致・skip・実ブラウザ起動/終了を観測できない場合はinconclusive。この検査は採用テストツールを用いた限定された実行制約だけを証明し、一般の能力閉集合、PI、Process間境界、外部providerの真正性を証明しない。

採用済みNode/NestJS/PostgreSQLの限定実行基盤検査では `Compilation.runtime_constraints` に `cat-node-service-technology/v1` を指定する。`repository`、`check`（`runtime-` prefixの既存Work内named Node test）、`package`（サービスpackage.json）、`engine_package`（Node enginesのpackage.json）、`postgres`（`database / migrations / table / column`）と、NestJSを宣言した場合の `nest`（`module / export / health_path / health_fields`）を接続する。実際のWork production paths、Binding、package/lockfile、migration SQL、必要なbuilt moduleをCheck入力に含める。実行時は明示的に使い捨てのloopback test DB/HTTPのみを許し、正規named JUnit証拠とruntime identity、npm lock一致、実Node engine、実PG接続・read-only migration inventory、必要なら公式NestFactoryによる実compiled moduleの隔離起動・loopback HTTP応答を確認する。対象試験は採用済み機能に関する実DB/HTTP試験を使用する。これは限定的な実装技術制約の証拠であり、任意のDB不変条件・本番Providerの真正性・PI/Process間境界の証明ではない。


### 複数Processの構造型とRecord内部Presenceの接続

Process合成の型包含判定では、閉じたRecordの各フィールドについて、値Domainの包含とPresenceの許容状態を**別々に照合**する。Presenceの状態集合は required={value}、optional={missing,value}、absent={missing}、undefined={undefined}。送り手が取り得る状態のすべてを受け手が許容し、値状態がある場合にそのDomainの包含まで証明できたときに限り、構造的にmatchedとする。

宣言されていないRecordキーは常にmissingとみなし、片側でキーが省略されていても受け手のoptional/absentが許容するなら証明できる。型参照が未解決・包含検査が不確定な場合はinconclusive、状態集合が非包含の場合はmismatchとする。Record内のnullableはnullの許容であり、missing/undefinedの許容と同一視しない。**Effect直接参照・PI間接続に共通する型包含では、`set<T>`から`set<U>`への変換について、要素値域`T ⊆ U`に加え、受信側Uの要素等価性が送信側Tで区別できる2要素を同一視しないことも必要**とする。実数Domainでは整数`1`と小数表現`1.0`を区別する一方、`json`の数値意味等価性は両者を同一視するため、`set<real> → set<json>`は要素値域が包含されても集合値域の包含を肯定証明できず`inconclusive`とする。入れ子Record/Sequenceやnullable/unionにもこの区別を保守的に伝播し、証明不能なら要素型だけから`matched`へ昇格しない。逆に、整数・文字列・enumの厳密値等価性が維持される対象や、`set<real> → sequence<json>`のように送信先が集合の重複禁止を要求しない場合は、通常の型包含証明を妨げない。この判定はEffect直接参照と型付きPIの**値集合と等価性**の構造検査であり、同じ値が実通信で届けられたことや外部Providerの真正性を証明しない。構造的matchedは**外部転送・実装・複数Process交錯の証明ではない**ため、これだけでProcess合成の最終CAT Gateをpassedにしない。

PI間の明示Bindingは**リンクした提供Operationと受付OperationそれぞれのPresence**を評価する。PIのFields表は既定値であり、Operation Presenceで`required / absent / optional / undefined`が上書きされていれば該当Operationの宣言を優先する。型包含だけでなく送受双方の許容Presence状態集合の包含を照合し、別Operationの上書きは伝播させない。受信側にBindingのないフィールドがあるかも**受付OperationのPresence**で判定する。元Fieldsの`absent`が対象Operationで`required`になれば接続義務が生じ、元Fieldsの`required`が対象Operationで`absent`になればそのOperationには値のBindingを要求しない。矛盾する二重Overrideは拒否する。この結果は型付き接続の構造的証拠に限定され、外部送受信の実証・実行者真正性・Sourceからの独立Model Conformanceを代替しない。

PI間の明示Bindingでは、同一受信フィールドへの複数送信フィールドの割当を曖昧として拒否する。受信PIの未接続入力Fieldに加え、送信PIの未接続出力Fieldも、実際にリンクした各OperationのPresenceで検査する。どちらかに`absent`以外のFieldが残れば、他のFieldの型が一致しても当該PI接続は`inconclusive`とし、`unmapped_target_fields`／`unmapped_source_fields`にField IDをそれぞれ保持する。`optional`（送信され得る）や`undefined`（単なる`absent`ではない）を暗黙の非送信扱いにはしない。現行Binding形式にはOperationごとのField射影の規範宣言がないため、接続済みの一部Fieldだけを根拠に送信・受信PI全体の完全接続を推測しない。対象Operationで明示された`absent`だけは値Bindingを要求せず、別OperationのPresence overrideは伝播させない。また、送信側が`absent`または`undefined`のみを取り得る場合、値が存在しないためDomain値域の包含を要求せず、Presence状態集合の包含だけを検査する。その際の`value_domain_proof: not-applicable`は値の証明を意味せず、JavaScript等の伝送実装の検証は依然`external_effects_verified: false`で未証明とする。`required`・`optional`など値を取り得る送信は従来どおり値Domain包含が必要。

`cat-process-bindings/v1`の各明示PI接続では、`field_links`は**省略不可の配列**だが、対象の提供／受付Operationで転送可能な値Fieldが無い場合（双方の関連Fieldが`absent`の場合など）、**明示的な空配列`[]`を認める**。非空の接続を強制するために架空の値Fieldを増やさない。一方、`[]`を指定しても、そのOperationで`required`・`optional`・`undefined`のまま残る未接続Fieldは`unmapped_source_fields`／`unmapped_target_fields`へ保持し、構造的接続の証明は`inconclusive`とする。空配列は外部通信の実行・結果やSource→Modelの意味保存を証明しない。

`cat-process-bindings/v1` に任意の `source_assemblies` を明示した場合、構造適合とは別に **Source-boundな有限接続関係** を検査する。全Modelに対する厳密な `model_sha256` と、Process IDをキーとする `source_assemblies` が必要。各値は `process`（単独Source参照）、`pis`・`tces`（非空の配列）、任意の `domain_rule`・`common_rules`・`domain_specs` を持ち、全Source参照は `{"path":"manifestからの相対パス","sha256":"実SHA-256"}`。Sourceの範囲・ハッシュと独立 `model-conformance` を検査した後、明示した提供／受付Operation・固定peer・requiredな全接続値の組を保持し、有限Scalarの全有効before状態から全宣言Outcomeを評価する。受信側の有効PI制約に違反する値組があれば `relation_status: refuted` と反例を返し、合成を `blocked` とする。有限全域で包含が成立すれば `relation_status: proved` を返す。未束縛・非required・非有限・未知関数・容量超は `inconclusive`。`source_assemblies` を省略した従来のModelのみの接続からは関係証明を得ない。入力SHAを正式Gateの証拠鮮度にも含める。この証明は親子境界に宣言された結果関係の局所包含であり、実送信・外部作用・全Processの実行相関・一般合成閉包を証明しない。


### 同一実行の因果相関診断（非規範・外部作用証明ではない）

`cat_execution_trace_diagnostic.py` は、観測提供者が別途収集した `cat-execution-trace/v1` の**形式整合性**を、対象 TestModel の実ファイルSHA-256と各規範SourceのArtifact ID/SHA-256に結び付けて検査する。出典PIのOperationと特定peerの対応は、元Modelに明示されたものだけを使い、多peerに対して省略された対応を推測しない。`@execution-origin`で明示されたPI相手／Operation相手は、各`runs[].execution_id`に対応した**具体的な**`runs[].peer`へ束縛し、別実行の相手や`@execution-origin`という記号そのものを実行元として受理しない。静的peerでは従来の一致検査を維持する。

入力は `--model TestModel.json --trace Trace.json --output diagnostics/execution-trace.json` とする。Traceは `model_sha256`、`source_sha256`（Source ID→SHA辞書）、`runs`（実行ID、受付Operation、peer）、`events`（event ID、実行ID、kind、parent_event_id、必要なOperation・peer・結果）を持つ。対応するイベントの `parent_event_id` は、同じ実行の**それより前のイベント**を指す。`kind`には `trigger/input/request/response/projection/replace/result/followup` を使う。 任意の`events[].outcome_index`が宣言された場合、JSONの正の整数でなければならず、真偽値・小数値・負数・0を拒否する。Traceイベントが`rule_id`を明示し、TestModelに`rules`一覧がある場合は、Rule IDの実在と、併記された`outcome_index`が当該RuleのAllowed Outcome個数以内であることも構造的に照合する。Modelに存在しないRuleや結果番号を宣言したTraceは`blocked`とする。同一`execution_id`かつ同一Rule IDに対して複数イベントが**明示的に**Allowed Outcome番号を宣言するとき、それらは同一番号でなければならない。個々の番号がそれぞれModel上の有効範囲内でも、同一論理実行で相異なる選択結果を同時に主張すれば`blocked`とする。異なる実行間・別Rule間のOutcome選択は混同せず、省略された番号は補完しない。**元TestModelの受付OperationとRuleの両方にTriggerが明示されている場合**、各実行の`entry_operation`のTriggerと、Traceイベントが名指すRuleのTriggerは一致しなければならない。どちらかの束縛が宣言されていない旧Modelではその対応を推測・検証済み扱いせず、従来の限定形式診断を維持する。一方、Rule宣言自体を省略したイベントや、旧合成ModelでRule一覧を持たないTraceではIDを推測しない。この検査は提出されたTestModelに対する整合性だけであり、Source→Modelの独立意味保存や実行の真正性・規範上の結果成立を証明しない。`cat_effect_trace_correlation.py`でもEffect receiptが名指すRule IDと当該runの受付Operationが持つ明示Triggerを突合し、Trace内のRuleイベントが省略されていても、**別TriggerのRuleを当該実行へ結び付けるreceiptは拒否**する。観測済み・`not-observed`のいずれも同じ宣言整合性を要求し、出典にないTrigger・実装順序・Provider時点を補わない。要求応答型のv1 Traceで`response`イベントは**同一実行に属する先行`request`祖先**を必ず持つ。要求と応答の間に中間処理イベントを挟むことは許容するが、`trigger`や無関係な`input`を応答の起点として借用することは拒否する。任意の`runs[]`や`events[]`に`correlation`が明示された場合は必ず正しいID組の形式を検査し、特に同じ実行のrunとその単一terminalに**両方とも**IDがある場合は一致を要求する。別枝の独立副作用は同じIDに固定しない。`request`・`response`がそれぞれ任意の`correlation`（`request_id`／`transaction_id`／`target_id`）を**明示**した場合は、完全な非空ID組であることを検査し、同一の因果関係にある要求・応答がともにIDを申告していれば値の一致を要求する。Effect receiptとの相関評価では、receiptに結び付く**Effectイベントまたはterminalイベントの祖先経路上**の`request`・`response`が明示したIDのみをreceipt側と照合する。同じ実行内であっても別枝の独立要求に相異なるIDが付くことを一律に禁止しない。`not-observed`のreceiptについても、存在するterminalの因果経路上に明示的な矛盾があれば拒否する。省略されたCorrelation IDや未申告の通信イベントを補完せず、同一実行の自己申告ID整合性をHTTP/DB/Discord Providerの真正性証明へ昇格しない。`request/replace/followup`のTraceイベントが**Rule ID・Allowed Outcome番号・Effect作用先をすべて明示**した場合、Modelの当該Rule／当該Outcomeがその作用先へ書込むことを検査し、不一致は`blocked`とする。Receipt相関では、観測済みEffectの`effect_event_id`を明示イベントへ一対一に束縛し、`not-observed` receiptは同じ実行・Rule・Outcome・作用先に対する未観測の申告1件としてのみ照合する。明示Effectイベントの対応receiptが欠ける場合は`trace-effect-without-receipt`、Rule／Outcome／作用先の一部しか宣言されない場合は`trace-effect-binding-incomplete`として`unresolved`に保持し、`identity-consistent-only`と誤表示しない。元TraceにRule等の証拠識別が存在しない旧イベントについて、作用先や実行済みEffectを推測してreceipt要求を新設しない。欠落・`not-observed`はいずれも`inconclusive`であり、実Provider未認証・Source→Model意味同値未証明は変わらない。応答を根拠にした射影 `projection.source_kind=response` は同一実行のresponse祖先を要し、`followup` は結果祖先を要する。

別実行のHTTP応答や別peer向け提供Operationを混ぜたTrace、二重terminal、Source・Model SHA差異、Operationが曖昧な多peerは`blocked`として拒否する。結果が `unknown`、またはterminal自体が存在しない実行は、形式が矛盾していなくても `trace_integrity: inconclusive` を返す。結果が成功・失敗のどちらでも、Trace自体の形式整合性を実測外部作用の成功に置き換えない。

**保証境界**：実行者・ログ発行者の真正性、HTTP/HOCON/DB/Discordの実効果、正しい射影、atomic replace、権限/ロック、時刻順序の物理的保証、外部配送や一般のProcess合成をこの診断は確認しない。動的実行元のTrace内での一貫性も**自己申告の内部整合性**であり、実際にそのProcessが起動したことを独立に証明しない。`normative_status: inconclusive`、`formal_gate_status: not-run`、`external_effect_proof: not-run` を固定し、CATのProcess ClosureやImplementation Conformanceへ`passed`証拠として渡してはならない。Source→Traceの意味同値を採用するには、別途承認された契約と真正な独立観測Providerが必要である。

**GEN-03 Trace profile方針（採用、追加profile未実装）**：このv1は要求応答型の既存診断プロファイルであり、購読・継続通知・複数の中間観測について1実行1terminal等の制約を普遍的CAT仕様にしない。購読／streamの意味が採用済みPI/TCE・観測契約として定まった場合に、互換性を保つ**別profile**を設計する。現段階では非対応profileを検証したと称さず、v1に未知eventを混ぜた入力の従来の`blocked`を弱めない。

### marker/style関係の限定的なfixture診断（規範Gateではない）

この診断は**任意の適用先向けプロファイル**であり、CAT-TDD共通のPI/TCE/Ruleの唯一の合法表現ではない。共通部品 `catlib/fixture_probe.py` は元Source/fixtureの生SHA-256・Artifact ID・DomainSpec種別・Rule ID実在を確認し、`normative_status: inconclusive`、`formal_gate_status: not-run` の出典エンベロープを作るだけで、**関係述語の判定や正当な仕様採用を行わない**。固有の `validated.api_markers`・`api_styles`・`marker_styles`・`owner.kind` などの解釈と参照検査は任意プロファイル `catlib/diagnostic_profiles/marker_style.py` 内に隔離した。既存CLI `cat_relation_diagnostic.py` はこの旧プロファイルだけを選択する互換入口であり、他の射影を同じ意味だと自動推測しない。

別の技術・射影を使用する適用先は、共通部品でSource/fixture同一性を検査した後、**その適用先が定義・検証した個別述語**を別途実行する。SourceとIDが一致するだけでRule意味同値・外部真正性を `passed` にしてはならない。この共通部品を正式CAT Gateに登録したり、新しい汎用関係DSLを導入したりする変更ではない。

`cat_relation_diagnostic.py` は、`cat-relation-probe/v1` で**実際のDomainSpec元バイトとfixtureバイトをSHA-256で固定**し、指定されたDomainSpecのArtifact IDとRule IDの実在を検査した後、サポート済みの `marker-style-references/v1` だけを実行する。この限定述語は、fixtureの `validated.api_markers[].id` の重複、`validated.marker_styles[].marker_id` の未知参照・重複・未割当、styleと `validated.api_styles[]` の構造一致、marker `owner.kind` とstyle `owner_kind` の一致を調べる。別markerが同じstyle値を共有することは許容する。列・色値・markerの順序は自動で書き換えない。

診断呼出しは `--source SOURCE.md --fixture FIXTURE.json --contract CONTRACT.json --output RelationReport.json`。入力契約は `source_artifact`、`source_sha256`、`rule_id`、`fixture_sha256`、`relation` を保持する。`validated` が存在しない場合は `status: inconclusive`、参照不整合は `failed`、矛盾が検出されなかった場合も `status: passed-fixture-only` に限定する。**どのケースでも `normative_status: inconclusive`、`formal_gate_status: not-run`、`external_hocon_status: not-run` を維持する。**

これは可視fixtureの閉じた参照関係を調べる用途であり、HOCONの継承/上書き、承認色、4カテゴリ規則、DOM/line/shape描画、外部応答の真正性、結果通知やファイル置換、Ruleの自然言語要求と検査述語との同値は確認しない。未承認CandidateのRuleを正当なConfirmedとみなさず、既存の `cat_verifier_contracts.py` の本番Rule判定やProcess Closureへこの結果をそのまま合格証拠として渡さない。

### 有限Guard・非有限値域・Rule未証明の理由診断（非規範）

`cat_coverage_diagnostic.py --model TestModel.json --output CoverageDiagnostic.json` は、元Compilerが生成した**現行TestModelバイト列**をSHA-256で固定し、その `coverage_checks` の各 `proved/uncovered/conflict/unproven` を変更せず理由だけを集計する。有限Guardの未被覆・重複、65536通りの直上にある有限組合せ、明らかな非有限Domain（文字列・実数・無界整数・配列等）、未解決の名前付き型、Record内部のundefined、非required Effect読み込み、計算できない原因を区別する。型参照・Recordの内側へも診断対象を辿るが、無限値域に対する有限サンプルを使って全域を証明しない。

非証明理由の出典粒度は次のとおり。Compilerが `ordinary expression reads missing/undefined field …` を返したときは、ModelのFieldの `role`・基本Presence・所有PIと該当Triggerの受付Operation／操作別Presenceを一緒に示し、**通常値を読む時点で存在が保証されない**という現行Compilerの未証明理由を独立した `ordinary-input-read-without-presence` として表す。`nonfinite or too-large domain/Presence` の場合は、当該TriggerのModel Guard ASTから、`is-present/is-missing/is-undefined` のみで参照した項目を通常値読取と区別し、**非requiredな項目を通常値として読む箇所**を `nonrequired-ordinary-guard-value-read` として併記する。前者はCompiler理由の分類、後者は提出Modelの構文上の所在であり、元Source・実行環境の意味は独立に証明しない。`uncovered` に対して当該TriggerのローカルTCE RuleがModel内に無い場合は `trigger-without-local-tce` を併記するが、他Processへの正当な委譲の有無は判定しない。`conflict` ではCompilerが残した具体的重複WitnessのRule ID集合と最初のWitnessを保持するが、現実の状態到達性・本番での矛盾を確定しない。未被覆の具体例は最大3件だけ参照し、計数値が `null` の場合は正確な総数を装わない。これらはすべて `submitted-TestModel-only` の診断注記であり、製品に特殊なRule名・依存関係をRuntimeへハードコードしない。\n\n未検証 `rule_obligations` はSource Artifact ID/SHAと元の `verification_contract` を保った `unverified-normative-rule` として列挙し、`unverified_effect_ids`、`unresolved_interfaces`、`unresolved_domains`も変更せず残す。Sourceのハッシュ参照がModel内部で矛盾するときは診断を拒否する。ただし、この内部照合は**独立した元Source読取・Model Conformanceではない**。診断結果の`status: diagnostic`、`source_conformance_status: not-run`、`process_closure_status: not-run`、`formal_gate_status: not-run`は正式CAT Gateの実行結果と混同しない。規範Ruleの自然言語意味の同値・外部Effectの実観測、非有限Guardの一般証明は別責務のまま残す。

### 外部EffectのSource・実装・Driver・観測ファイル対応（非規範）

`cat_external_effect_receipts.py` は、`cat-external-effect-receipts/v1` の提出証拠が**現在読み込んだModelバイト・Source ID/SHA・Driverバイト**と一致し、宣言されたTCE Rule / Allowed Outcome / Effect target / 実行IDに結び付くかだけを検査する。実装HEADは40桁commit識別子として記録するが、Checkoutとの独立照合が無いときは `implementation_head_checkout_verified: false` を明示する。

入力は `--model TestModel.json --packet Receipts.json --driver DriverFile --observation-root Directory --output Result.json`。packetには `model_sha256`、`source_sha256`、`driver_sha256`、`implementation_head`、複数の `observations` を指定する。各観測レコードは `rule_id / outcome_index (1-origin) / effect_target / execution_id / reported_status / observation_file / observation_sha256` を持ち、当該ファイルのJSONと照合する。観測の `reported_status` は `succeeded/failed/unknown/not-observed`。`not-observed` は観測ファイルを持たないことを要求し、`unknown` は報告値が成功へ変わらない。誤Outcome、非宣言Effect、二重receipt、**同一execution_id・Ruleに属する排他的な複数Allowed Outcome**、別実行ID、古いSource/Model/Driver SHA、観測ファイルのすり替え・Root外参照を拒否する。同じAllowed Outcome内の異なるEffect targetの観測は引き続き許す。この整合性判定は実際に選ばれたOutcomeや外部作用の真正性を証明するものではない。 観測JSONが `correlation` を明示する場合は `request_id / transaction_id / target_id` がそれぞれ空でない文字列であることを要求し、Effect receiptの同名3値との一致を検査する。観測ファイル側だけにIDがありreceiptに存在しない場合や、両者が異なる場合は`blocked`。従来の観測JSONがこの任意項目を持たないことだけでは拒否しない。同じ`execution_id`に属する複数のEffect receiptが`correlation`を1件でも宣言した場合は、**その実行に属する全receiptが同じ`request_id / transaction_id / target_id`の3値を宣言**しなければならない。観測済みと`not-observed`の双方に適用し、矛盾・一部欠落を`blocked`とする。一方、異なる実行間のIDの違いや、当該実行のreceiptがすべて相関未宣言である旧形式は許容する。観測内容のSHAが一致しても、IDの一致・外部Providerの真正性・transactionの実際の終端証明はそれぞれ別である。

結果の `status: consistent-receipts-only` は**提出されたファイル群の内部整合性**であり、実装が外部作用を行ったと証明するものではない。全件で `normative_status: inconclusive`、`formal_gate_status: not-run`、`implementation_conformance_status: not-run`、`provider_authentication_status: not-run`、`external_effect_proof: not-run` を保持する。実在Providerの証明書・採用済みSource述語・同一実行トレース・環境別Driverの意味同値が無ければ、Greenやmock JSONをProcess Closure／Rule／Implementation Conformanceのpassedへ接続しない。`cat_verifier_contracts.py` のfixture観測結果を実外部効果の証拠として流用しない。

### 同一実行TraceとEffect receiptの正式Work入力照合

`cat_effect_trace_correlation.py` は、単独の診断器が証明しない **同一実行・同じRule/Allowed Outcome/Effect target・同じSource/Model SHA** を、互いに独立に提出されたTrace (`cat-execution-trace/v1`) とEffect receipt (`cat-external-effect-receipts/v1`) の形式間で照合する。各観測済みreceiptには `effect_event_id` を明示し、Traceの `request/replace/followup` イベント1件と一対一で対応づける。イベントと最終resultには `rule_id` / `outcome_index` を使い、別実行、存在しないイベント、宣言外target、別Rule/Outcome、同一イベントの再使用を拒否する。対応するEffect eventの `outcome_index` は、Sourceに宣言されたAllowed Outcomeを指す**1始まりの正の整数**でなければならない。terminal resultでも `outcome_index` を明示する場合は同じ整数型を要求し、JSONの`true`/`false`や`1.0`を整数のOutcome番号として扱わない。terminalのRule/Outcomeが省略されている場合は形式整合でも `inconclusive` とする。Effectが `not-observed` であっても、同一実行のterminalが明示したRule/Outcomeとreceiptが異なるなら証拠の矛盾として `blocked` とし、単なる証拠不足に混同しない。明示のないterminalや未観測Effectは引き続き `inconclusive` とし、`unknown` や `not-observed` を成功へ昇格しない。

**同一要求・transaction・対象の明示相関（任意の診断拡張）**：同一実行のTrace `runs[]`、Effect `observations[]`、対応するEffect `events[]`、存在するterminal `events[]` に `correlation: {"request_id": "...", "transaction_id": "...", "target_id": "..."}` を宣言できる。この3値はいずれも空でない文字列を要求する。関係する証拠のいずれかが相関を宣言した場合、照合対象すべてに同じ3値が存在しなければ `blocked` とする。観測できなかったEffectはEffect eventを要求せずrunとreceiptを照合する。terminalにも**相関IDが明示**されている場合は同一実行のrun・receiptと一致しなければ拒否するが、terminalへの相関IDが未宣言であることだけで新たな観測を捏造したり`passed`へ昇格しない。terminalが存在しない場合も、未観測を `inconclusive` に保つ。旧Trace/receiptで全件未宣言の場合は従来の `execution_id` のみの照合を維持する。これは**提出されたID間の一貫性**の検査であり、実transactionのcommit/rollback、HTTP応答からのDB終端推論、Providerの真正性や全実行関係のSource同値性は証明しない。失敗応答と確定rollbackを同一視しない。

Workの `## Compilation` に追加できる列は `Effect trace` / `Effect packet` / `Effect driver`、必要な場合のみ `Effect repository` / `Effect driver repo path`。前者3つは**全件同時指定**が必須、旧Workでは全て省略可。各ファイルpathは他のCompilation入力と同じ境界制約を適用する。任意のWorkで `compilation.effect_trace` 等の同名keyも使用可能。`Effect repository` には Work の宣言済みリポジトリ名、`Effect driver repo path` にはそのcheckoutからのDriver相対pathを指定する。両者がある場合だけGitの実HEADとそのcommit内Driver Blob、作業ツリー実バイトを独立照合する。Driverの**実行**とProviderの**真正性**までは推論しない。

`cat_flow.py conformance --kind implementation-conformance` はこの3入力があれば `.cat-flow/cache/implementation-effect-correlation.json` へScript検査結果を書き、誤bindingを `blocked` にする。実Model・Trace・packet・Driver・参照された観測ファイルをコンテンツSHAで `cat-conformance-evidence/v1` の完全入力集合に含め、内容が変化すれば `stale` とする。**形式照合が整合する場合でも、提出者の記録が真実か、外部作用が実際に発生したか、自然言語Ruleの意味と検査述語が同値かは未証明である。**この入力を提供したWorkのimplementation-conformanceを、他項目が全passedでも本照合の成否のみで `passed` にしない。`inconclusive` は欠陥を隠すための値ではなく、真正Providerと採用済み形式契約が不足することを明示する。

個別CLI:

~~~sh
python .cat-system/scripts/cat_effect_trace_correlation.py \
  --model Model.json --trace Trace.json --packet Receipts.json \
  --driver DriverFile --observation-root ./observations \
  --output diagnostics/EffectTraceCorrelation.json
~~~

### 規範RuleのVerifier観測と独立証明の分離

`cat-verifier-result/v1`の`status: passed`は、登録されたrunnerが固定fixtureを読み取り、assertionと一致する観測JSONを返したことを意味するだけである。Verifier結果には`verification_scope: fixture-assertions-only`と別の`normative_status: inconclusive`を明示する。`process-closure`は**検証実行の`status`と規範の`normative_status`を区別して**評価する。Workに`verifier_registry`を明示した場合は、**全適用Ruleがすでにintrinsic proofで証明されているときも、登録Verifierを省略せず検証する**。RegistryのModel SHA不一致・未知Rule ID・実行された失敗assertionはGateで`blocked`とする。ただし、自由文の未証明Ruleはfixture成功だけでは閉包せず、証明済みintrinsic Ruleについては任意に追加したfixtureの未実行を理由としてSource-bound構造証明を取り消さない。登録assertionの`status: failed`は提出された検証証拠の不成立としてGateを`blocked`にするが、その事実だけで自由記述Ruleの意味が偽と証明されたとは扱わない。assertionが`passed`であっても`normative_status: inconclusive`ならRuleの規範義務は残り、最終Gateは`passed`にならない。CommonRule/DomainSpecの自由記述Requirementとassertionの**意味的同値は証明しない**。そのため、Rule義務を任意のrunner観測成功だけで`passed`へ昇格しない。

Processの適用外であることが、完全なProcess ID列挙を持つ規則の`scope_binding`（`cat-rule-explicit-process-scope/v1`、Source SHAと対象Process）から機械的に確認できる場合、当該Ruleの`verification_status: not-applicable`は**検証未実行のRuleではなく、そのProcessには義務が存在しないという限定的な判定**として扱う。元Rule・適用条件とScope証拠はTestModelの`rule_obligations`に残す。`cat-implementation-obligations/v1`は当該Processに対する`normative-rule.*`項目を生成しない。`cat-verifier-result/v1`は`normative_rule_inputs[].process`に保持した宣言元Process、同RuleのSource SHA、評価Processが宣言元の子孫であること、明示対象が宣言元配下であることを照合し、`status: not-applicable`と`verification_scope: explicit-process-scope-only`を区別して返す。適用外Ruleにfixture runnerを登録すること、およびScope証拠を偽造・不整合にすることは拒否する。他の適用内Ruleのfixture判定は適用外Ruleの未実行によって`inconclusive`へ汚染しない。**適用内Ruleでも**、Sourceが完全Process ID列挙を宣言している場合は、Verifierが宣言元Process・元Condition・現在Process・`scope_binding`を再照合する。出典Rule自身の`source_sha256`／`source_kind`と`source_records`の種別も照合し、ModelとRegistry双方のSHAを更新しても、改変した明示Scope・Rule出典を持つfixture実行を受理しない。各Ruleのreceiptには`source_sha256`、明示Scope、元Ruleレコードの決定論的`normative_rule_sha256`を残す。**この指紋はModel内部のRule表現を識別するだけで、原Sourceの独立検証や自然言語意味証明、署名、実Provider観測を代替しない。**ただし、この結果は**Ruleの要求そのものの真偽・外部Providerの振る舞い・別Processでの適用可否**を証明せず、規範全体の`normative_status`を`passed`へ昇格させない。真正の規範帰属は独立Source→Model Conformanceで別途照合する。

`cat-implementation-obligations/v1`は、正規Compilerが入力Artifactから作った限定的な`cat:intrinsic-model/v1`の構造証明とソースSHAを保存する。**最新の独立Model Conformanceがpassed**で、Rule ID・Artifact ID・SHAが完全一致する場合だけ、その構造述語に対応する`normative-rule`義務を局所的にpassedとする。これはModel自身の構造を証明するものであり、Discord/DOM/DB等の外部実装やrunnerの意味同値を保証しない。一般的な自然言語Ruleと外部観測だけの場合は`inconclusive`を維持し、全体`implementation-conformance`を根拠なく通過させない。

## CAT conformance

`cat_flow.py conformance --kind process-closure|model-conformance|implementation-conformance`を使用する。

JSON TestModelの`source_semantic_map`（Process／PI／TCE／CommonRule／DomainSpec／DomainRuleの出典・構成・範囲）、`pi_artifacts`、`local_coverage_requirements`は、正規Compilerの自己申告ではなく、**独立Source→Model Conformanceが元Sourceから別経路で再構成して照合**する。出典ID・TCE Outcome数・PI Field／Operation一覧・局所Coverage要求の欠落や改変は`blocked`とし、Compilerの出典対応表だけを根拠に規範上の帰属を証明した扱いにしない。加えて`model_type: symbolic-relation`、`normalized_ir`と`limits`（`finite-guard-closure-only`、`no-general-reachability-proof`、`no-process-composition`）は提出Modelから削除・上書きして証明範囲を広げられない。この一致検査は**Sourceの構造・証拠の範囲**のみを保証し、自由文Ruleの意味証明、初期状態からの一般到達可能性、外部Provider真正性、複数Processの全実行関係を新たに証明しない。

- process-closure: 現行compilerが証明可能な単一Process有限領域を機械判定する。**Compilerが生成したJSON TestModelを同じ原Process/PI/TCE/CommonRule/DomainSpec/DomainRuleから独立Source→Model Conformanceで再照合し、`passed`を得てからでなければ正式Closureを`passed`にしない**。独立照合が不一致・証明書改竄・Source SHA差異を検出したら`blocked`とし、正規Compiler出力の見かけの`confirmed`／`proved`や提出Verifier fixtureで上書きしない。正規照合の結果は`.cat-flow/cache/process-closure-source-model.json`へ保存し、成功したGate receiptは`source_model_evidence`として参照する。この追加チェックは限定intrinsic構造Rule証明を再確認するもので、自由文Rule、到達可能性の未形式化部分、外部Providerの真正性を新たに証明しない。TCEの網羅要求が`partial`なら、その局所結果だけでProcess全体をclosedとは扱わず`inconclusive`とする。multi-Process composition等もinconclusive。
- model-conformance: sourceからの完全再生成一致を判定する。
- implementation-conformance: deterministicに再生成一致した`cat-implementation-obligations/v1`をcategory別に集約する。各obligationは`source_ref / method / limitation`を必須とし、passed/failedはevidence、not-run/inconclusiveはreasonを保持する。failedはblocked、not-run/inconclusiveはinconclusive。

各conformance実行は `.cat-flow/conformance/<gate>.json` に入力hash・Work context・verdictに加えて、**現行のCAT-TDD本体Python実装（Technology SkillのInspectorを含む）と `config/routing.json` を全ファイル相対path・コンテンツSHAで固定した `runtime_sha256`** をScript所有の証拠として保存する。`status`はその完全な実行基盤fingerprintも再計算し、検証器・Compiler・Inspector・routingが更新された後の旧receipt、またはこの新規fingerprintを欠く旧receiptを`stale`として再検証を要求する。個別の無関係なPythonファイル更新でも安全側にstaleとなり得るが、Source・Work・実装HEADが同じまま判定器が変更された事実を見落とさない。これは現行インストールの**バイト一致**検査であり、署名・実行されたコードの真正性、外部Providerの観測、第三者による証拠改竄防止を保証しない。Work本文の自己申告だけでCAT適合性Gateをpassにしない。inconclusiveだけを対応Reviewerへ委譲し、そのReview evidenceで閉じることができる。failed / blocked / stale / not-runをReviewerでpassへ上書きしない。

## Scope ordering

`scripts/cat_scope_order.py`はWorkの`parent / depends_on`だけを入力としてcycle、dependency readiness、depthを計算し、ready集合のうち最深scopeを返す。Process closure側では同一Processに属する複数TCEをassembled inputとして合成し、個別TCEがpartialでも合成領域がclosedならpassできる。依存関係そのものの意味はAI/仕様側が与える。

## Write guard

書込みを持つAgent stageではwrite guardは任意ではない。`cat_flow.py handoff --stage ...`がpre snapshotを自動作成し、Agent終了後の`cat_flow.py guard --stage ... --phase finish`がpassedになるまで次stageへhandoffできない。write set外差分、禁止Artifact変更、pending/blocked guardのbaseline再作成を拒否する。標準`Lifecycle/Works`配置ではpre guard時にdeepest-readyも機械確認する。

Refactorではさらに`refactor-baseline`のpassed evidenceと現在source contextの一致をpre guardで再検証する。baseline後にsourceが変わっていればstaleとしてrefactor Agentを起動しない。

## Structured handoff

`cat_flow.py handoff --stage ...`はWork ID、flow/stage、executor、permissions、source hash、current Queue item、unresolved decision、evidence refs、stale inputs、next permitted actionをJSONで返す。自由文handoffを再読用正本にしない。

## Normative promotion

confirmed昇格は通常Agent/Reviewerの書込みではなく、明示されたnormative decisionを受け取る専用authority executor `scripts/cat_promote.py`がcandidate/draftを別のconfirmed配置へ移動しながら`status / decision_ref`を更新する。意味の決定そのものはこのScriptで行わない。

移動対象Artifactへの自己参照を含むMarkdownリンク（インラインおよびreference-style）は、旧sourceファイルを削除する前に新しいconfirmed配置のファイル名へ付け替える。`#fragment`のみの自己参照はそのまま保持する。外部参照・他ファイルへの相対参照は従来の検査・rebaseを適用し、解決不能なら元Artifactを破壊せずblockedとする。
