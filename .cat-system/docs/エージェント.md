# エージェント責務

| Agent | 所有する判断・出力 | 書込み境界 |
| --- | --- | --- |
| `orchestrator` | 人間のIssueを入口に工程を開始し、Issue→Task→Work分解を`cycle-scope-divider`へ委譲。規範、未決定事項、委譲、最終照合を管理 | Workflow台帳と統合報告 |
| `cycle-scope-divider` | 人間が提示したIssueをTask(Process)→Work(独立検証可能な仕様差)へ分解し、Task/Workを生成 | Lifecycle/Tasks・Works |
| `cycle-git-manager` | Git branch、worktree、commit、pushと、利用先のレビュー/CI/mergeの実状態 | Gitメタ操作、進捗証拠 |
| `cat-reverser` | コード・テスト・ログの観測から候補の復元 | CAT/Candidates |
| `cat-designer` | 承認済み要求からProcess/PI/TCE/Rule Draft | CAT/Draft |
| `cat-reviewer` | 閉包、参照、意味整合性、規範承認の分離 | Review。明示権限時だけ正本化 |
| `cat-test-modeler` | confirmed仕様の区別・遷移・許容結果・不変対象の保存 | TestModels |
| `tdd-test-generator` | モデルから実行可能なテストの選択と生成 | テストのみ |
| `tdd-reviewer` | モデル由来のoracle・テスト信頼性の審査 | Reviewのみ |
| `tdd-checker` | Red/Green/回帰/制約の実測判定 | 実行ログ・ゲート報告 |
| `tdd-implementer` | 対象Workのテストを満たす実装 | 本番ソースのみ |
| `ref-scoper` | 観測意味を保存する対象と順序の決定 | Refactor計画 |
| `ref-refactor` | 許可された範囲の内部構造の簡約 | 本番ソースのみ |

## Issue受付時の責任分界

通常の新規開発では、人間はIssueとして要求・問題・目的・完了条件・未決定事項を提示する。Task/Workへの構造化はAIの責務であり、`orchestrator`が`cycle-scope-divider`へ委譲する。人間可読なTask/Workはレビュー可能性のための形式であり、人間による手作成を前提としない。AIが意味上の選択を確定できない場合だけ、その選択を人間へ返す。

## 設計変更

従来の「候補作成→自動承認→正本化」は分割する。形式的な整合性の合格は仕様の意味を決めない。`cat-reviewer`は規範上の決定出典がある場合だけ正本化できる。`cat-reverser`の出力は実装事実のcandidateであり、bugも含み得る。

モデルとテストの間に`cat-test-modeler`と`tdd-test-generator`を置き、テスト期待値が実装コードに依存しない経路を明示する。監査者が同じモデルを使っても判断の独立性は保証されないため、監査は証拠から追跡する。

13種類は責務の識別子であって13個の並列プロセスの起動要件ではない。小さなWorkでは一つの実行主体が順次複数役割を担当してもよいが、意味決定と検証根拠を混同しない。

Orchestratorから呼ぶagentを固定ホワイトリストにはしない。利用可能な別agentに委ねる場合、対象成果物、規範基準、書込み範囲、期待出力と不可逆操作の承認要否を明記して委譲する。外部agentが自身の裁量で仕様や正本を変更することは許さない。

## Skillsとの関係

Agentは専門職責、Skillは手順。Agent frontmatterに全Skill名を列挙せず、`description`に入力・生成物・呼出し局面を含める。プロジェクト固有の技術・環境能力は追加Skillとして独立させる。あらゆるSkillを常時読み込ませない。

## 技術・Gitホストの非固定化

GitはCycleの前提だが、GitHub上のrepoは前提ではない。`cycle-git-manager`のGit操作と、PR/MR・CI等のホスト固有操作を区別する。Agentの職責にGitHub Actions等を組み込まない。技術スタックはプロジェクトの現行技術構成文書から読み、必要な`tech-*` SkillをWorkごとに選ぶ。静的なプロジェクト情報は文書、再利用可能な手順は技術Skill、なお残るプロジェクト固有の手順のみ`<project>-adapter`とする。詳細は[プロジェクト適用](プロジェクト適用.md)。


## 機械化された実行境界

Agentはコードで判定できる事項を自然言語で再判定せず、[AI実行契約](AI実行契約.md)にあるCLIを呼び出す。orchestrator/`cycle-scope-divider`は`validate`・`route`・`handoff`、`cycle-git-manager`は`git`、`cat-reviewer`は`.cat-system/skills/cat-specification-gate/scripts/cat_artifact_lint.py --files`、`cat-test-modeler`/`tdd-test-generator`は適用可能な`compile`、`tdd-checker`は`run`とJUnit証拠を使う。未対応の仕様は独立レビューへ分離する。いずれも`passed`のラベルから意味承認・実環境成功を推論しない。追加の独自Agentを使う場合もこの入出力契約を維持する。

## 定義と実行可能性の差

Agent定義の存在と、実行環境で強制される能力は区別する。標準13役割は`config/routing.json`の工程へ接続し、`tdd-reviewer`を`test-review`、`ref-scoper`を`refactor-scope`として生成・変更担当から分離する。追加Agentはroutingに無い限り自動実行されるとは扱わない。Agentのtools定義とCLI実行手順は一致させ、`成果物・変更可能範囲`という**文章だけをファイル書込み制限として扱わない**。Orchestratorから追加Agentへ委譲する場合も、委譲先の成果物・権限・復帰条件を明示する。

実運用前に、各Agentの**入力、権威、使用可能ツール、書込み対象、出力、独立Reviewer、停止条件**を実行環境へ対応付ける。Agentの職責を増やすこと自体を目的にせず、定義済み13役割とCLIの接続を検証する。禁止操作が実際に拒否されるかはCopilot実機・OS権限・CI等の境界で検証する。
