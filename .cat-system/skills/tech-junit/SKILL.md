# JUnit test realization


1. Confirm JUnit Platform/Jupiter versions, Maven/Gradle test plugin, tags, lifecycle, parallel settings, and result-report path from project files and technical documents.
2. Map TestModel partitions and TCE cases to tests/parameterized cases with expected outcomes derived from confirmed CAT artifacts, never from implementation output. Preserve CAT traceability where the project supports it.
3. Keep fixtures, extensions, lifecycle scope, mocks, and temporary resources isolated. Do not rely on test execution order unless the specification and project configuration explicitly require it.
4. Use Spring or other framework contexts only when the tested boundary requires them; a plain unit test should not acquire a broader context merely for convenience.
5. Record Red/Green/regression with the project-approved build command and JUnit XML/results when configured, including the exact selected test scope.

## Deterministic CAT v2 JUnit generation (bounded adapter)

`cat_compile_v2.py tests --framework junit --queue ...` selects a JUnit Jupiter source renderer while retaining the same confirmed TestModel, deterministic vectors, one-current-item Queue and source-bound oracle. Its `cat-junit-driver-binding/v1` declares `process`, `test_package`, `test_class`, and `driver_class`. The explicit driver class supplies public `prepare`, `observeState`, and `trigger` methods, checked by Java compilation, and must observe actual behavior rather than return the specification expectation. Generated classes include a deterministic vector-ID digest in the Java class name. The class is package-private (allowed by JUnit Jupiter), so an explicitly chosen `--output` Java filename need not equal the generated class name. **Use a distinct output file for each current Queue vector**; class-name uniqueness alone does not prevent overwriting files when the caller reuses one `--output` path. Naming the file after the generated class also works.

The legacy adapter accepts required boolean/enum/64-bit integer scalar fields with Java map transport. An explicit `output_operation_transport: "java-driver-provides/v1"` also supports operation-scoped scalar output required/optional/absent Presence. `triggerProvidedOperations(List<String> operationIds, String triggerId, Map<String,Object> input)` returns the actual operation-to-field-map projection of **one logical execution**, including empty frames. The generated oracle checks the exact operation set, PI field ownership and one joint allowed state/output outcome. Unsupported input Presence, undefined, nullable/structured/temporal/set domains remain blocked. The opt-in `observation_transport: "java-driver-observed/v1"` supports only the proved finite trigger-entry observations of the Source. `prepareObservations(Map<String,Map<String,String>> scope, Map<String,Object> values)` configures the controlled environment, with source/peer/operation/cut metadata; `triggerObserved(List<String> operationIds, String triggerId, Map<String,Object> input)` returns `Map<String,Object>` with exactly `observations` (actual values read in this execution) and `output` (flat field map if no operation IDs, operation-to-field-map if combined with `java-driver-provides/v1`). Do not merely echo fixture values; the generated test asserts the actual observation inventory and values separately from the output/state oracle. This binding rejects unsupported observations/actions and cannot be combined with `pi-only-unverified`. For Process observation/action capability declarations, a caller may explicitly request **PI input/output-only** testing by adding `capability_scope` to its existing `cat-junit-driver-binding/v1` file with `kind: "pi-only-unverified"` and `observations`/`actions` lists containing **every declared capability ID exactly once**. Missing, invented or incomplete declarations fail closed. The generated JUnit source prominently states `CAPABILITIES NOT VERIFIED`, so passing these tests does not prove source observations, side effects, cross-Process behavior, runtime writer exclusion, or full Implementation Conformance. This is a technology adapter boundary, **not** a modification or implicit approval of the Confirmed TestModel. Any unsupported capability transport still requires a separate verified adapter; no capability is silently executed or claimed. Neither opt-in binding mandates a product implementation API or proves provider authenticity, external delivery or cross-process trace completeness. Red/Green and formal implementation-conformance still require Work-declared checks and Script-owned evidence.
